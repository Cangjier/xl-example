# OPEN-QUESTIONS — 开工前需要用户/Lead 拍板的问题

> 只列会改变**范围、验收口径或资源**的问题；实现细节已由 `PLAN.md` §4 裁决，不再问。
> 每条给：推荐默认值 + 影响面。用户在 checkpoint 回答后，Lead 把答案回填到 PLAN 对应小节。

## OQ-1 删除范围：408 个 `*possible*.xl.md`（18,099 行）是否全部硬删？

- **背景**：实测 408 个文件，其中 **232 个是零引用的纯 `throw` 桩**（keywords 84 / punctuation 61 / jsdoc 43 / jsx 12 / aliases 32 / literals 10 / trivia 9 / synthetic 7 / names 2 / bindings 3，加 core 4 中的部分）。
  它们不是本次重构要替换的逻辑，只是历史遗留桩；删掉它们会让 diff 很大但**零行为变化**。
- **推荐**：**全部硬删**（用户约束①已定「含全部 throw 桩文件」）；分两段删——先删 232 个死桩（零风险），
  shared 协议（`CatalogGuide` 等 4+2 个）最后删。
- **影响面**：`dist/ts` 文件数 872 → ≈465 + 新增 ≈480；删除提交是最大 diff（约 1.8 万行）。
  若选择「只删真实逻辑、保留桩」，则违反用户约束①，且 `grep possible` 不归零。

## OQ-2 最终集成是否允许「混合模式」（部分形态保留 legacy 目录）？

- **背景**：`design-gates.md` §9.2 建议性能/等价性不达标时「保留 possible 层作为未覆盖形态的兼容路径」；
  但用户约束①要求 possible 层**彻底删除**。两者在「某个形态实在等价不了」时冲突。
- **推荐**：**最终 `refactor-integration` 硬删、不允许混合**；混合模式只允许出现在**工作分支**上用于定位问题，
  且必须写成 HANDOFF 里的「未完成项」。若某形态确实无法等价转换 → 该包不能合并，报 Lead/用户重定范围（不静默混入）。
- **影响面**：决定 WP-7 的退出条件能否是 `grep = 0`；也决定万一 WP-3 卡住时是「降级混合」还是「阻塞等决策」。

## OQ-3 性能验收的「可测改善」是否按 gates 的阈值执行到底？

- **推荐**（= gates §4/§8 原值）：总 Parse 同轮配对 ≤1.05（上限 565 ms）；
  `class-scaling --base` 同规模 new/base ≤1.10、T=2000 ≤0.90、class/iface ≤1.8、相邻翻倍 <2.6；
  `statement-scaling --base` 同口径；最终验收**无并发时段**、3 轮 `--repeat 5` 取中位的中位。
- **需确认**：若最终只做到「不劣化」但没有「可测改善」，是否算**未达成验收**（gates §8.5 说算未达成，按 §9 处置）。
- **影响面**：决定 WP-F 的结论口径与是否需要追加优化包；也决定 `impl-wp2` 是否必须把 `statement-scaling` 修到绿。

## OQ-4 `tests/bench/statement-scaling.mjs` 当前崩溃，谁负责修、修好后是否进门禁？

- **背景**：gates 附录 A：脚本在生成语料上抛 `SyntaxException: 表达式没有读完`（生成源不受解析器支持）；
  该脚本由 `design-gates` 成员新增，属共享文件范畴。
- **推荐**：**WP-2 负责把脚本修到「可跑 + 达标」**（它最了解语句边界形态），修好后由 **Lead/共享文件 owner**
  决定是否加进 `gates.ps1` full 档（PLAN 建议：先作为 `merge-wp2` 的必跑项，WP-7 后再进 gates）。
- **影响面**：若不修，最终验收就少一条「长语句体可测改善」的证据，只能用手写语料替代（说服力下降）。

## OQ-5 共享文件（`set\tools\*.ps1`、`set\TEAM.md`）在实现阶段归谁改？

- **推荐**：仍归 **Lead / 指定一个 `gates-owner`**（design-gates 文档的作者）；实现成员**一律只读**，
  需要新门禁/参数时提交「需求 + 命令」给 Lead，由 owner 改。避免多人改 `.ps1`（BOM/PS5.1 坑）导致门禁脚本坏掉。
- **影响面**：决定 `statement-scaling` 进门禁、`gates.ps1` 加 `-BaseBuild` 之外的参数由谁落地。

## OQ-6 并发度与测量窗口：同一时刻允许几个实现成员跑门禁？

- **背景**：gates §2.1 实测同机并发会让 `parse-perf` 单次差 7–12%，class-scaling 可达 +35%。
- **推荐**：**最多 2 个实现成员并行**（本 PLAN 的并行组正好 2–3 个，波 3 是 3 个，需错峰跑性能门禁）；
  **所有性能判据只在空时段串行测**；WP-F 验收前 Lead 负责让所有 agent 停手。
- **影响面**：决定 Wave 3（WP-3/4/5 三并行）是否串成 2+1；也决定总墙钟。

## OQ-7 合并顺序：固定顺序 or 按完成顺序先到先合？

- **推荐**：**固定顺序** WP-0→1→2→3→4→5→6→7（PLAN §6.1），与并行执行无关；
  后完成的包在交付前 rebase 集成分支。理由：可复现、回滚点清晰、tag 语义稳定。
- **影响面**：若选「先到先合」，需要额外的 tag 命名与回归复测策略，merger 工作量 +1 轮/包。

## OQ-8 文档是否合入 `refactor-integration`？

- **推荐**：**合入**（docs-only，由 `merge-docs` 做）：实现成员的 clone 都基于集成分支，PLAN 在集成分支上
  才能被每个新成员直接读到，不必各自 `fetch` design-plan。设计原文（drive/bodies/gates 三份）可**只留在各自分支**，
  在 PLAN 里给路径引用；若 Lead 希望实现成员离线也能读，可一并 docs-only 合入。
- **影响面**：决定 `merge-docs` 的范围与集成分支是否含文档历史；不影响代码与门禁。
