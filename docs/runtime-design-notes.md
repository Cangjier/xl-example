# 运行时为什么要长成这样

[runtime-architecture.md](runtime-architecture.md) 写的是「怎么写」；这一份写「为什么只能这么写」。
每一条都先摆出候选、再说明它为什么不行，最后才是采用的方案——与
[cpp-design-notes.md](cpp-design-notes.md) 同一体裁。

本层要同时满足四件事，而它们互相拉扯：

1. **同一份规范要能转成 C++ / C# / Rust / TS** —— 不能用宿主专有的手段；
2. 要能跑**全量 TS** —— 动态类型、闭包、原型链、异常、迭代、异步；
3. 要**安全** —— 会跑别人写的脚本；
4. 要能被客户的 C++ 程序**直接嵌入** —— 没有 wasm、没有 JS 引擎也要能跑。

总纲一句话：**用数据表实现动态语义，而不是用宿主的反射和 GC 实现动态语义。**
前者能生成到任何静态目标语言，后者一条都出不去。

---

## 一、这一层要解决的四个问题

动态语言落到静态目标（尤其是 wasm）上，难的不是语法，是这四件事：

| 常见写法 | 本工程解析侧的实测计数 | 静态目标上的难点 | 本设计给的出路 |
| --- | --- | --- | --- |
| `this.constructor.name` | 202 | 没有可移植的运行时类名 | 整数 `cls` / opcode 分派；名字只在需要时查静态表 |
| `: any` / `new Map()` | 594 / 103 | 需要具体的内存布局 | 有标签的值 + 自有对象表 |
| `throw new` / `instanceof` | 162 / 989 | wasm EH 与 C++ 异常都不统一 | 静态 handler 表 |
| 虚分派 / 哈希寄存器 | — | 间接调用与哈希表 | `switch(op)` + 槽数组 |

**这四件难事全部搬进 VM 之后，wasm / C++ / Rust 只面对一个 `switch` 和一段线性内存。**

---

## 二、本设计明确避开的七种做法

这些是解释器里很常见、但在这四件事的约束下会当场失效的写法：

| 做法 | 为什么在本层的目标下不成立 |
| --- | --- |
| 用**宿主的运行时类型对象**给值打标签（值 + `Type`） | 那个类型对象在 C++ / Rust / wasm 里没有对应物；跨语言就没有「同一个类型」这回事 |
| 按**宿主类型**做算子派发（反射查方法表） | 反射调用无法生成到任何静态目标语言；而且每次算子是查表 + 间接调用 |
| 宿主对象按**宿主类型**作键 | 键本身就是宿主概念，换语言没有键 |
| 值走**一次性信箱**（读一次就删的哈希寄存器） | 每传一个值一次哈希插入 + 删除；而且「读」有副作用，语义脆 |
| 变量按**名字**查、作用域用字典链 | 名字查找与栈回退都是解释器时代的做法，且在编译期就能算好 |
| **下标是可变对象状态**（列表位置即下标） | 列表一改，下标就变 ⇒「程序不可变」不成立，跳转目标会漂 |
| 解析与执行**共用一套类层级** | 两件事的 IR 不一样：解析侧是 token 树，执行侧是字节码 |

---

## 三、被证伪的替代方案

### 3.1 IR / runtime 边界取「高层算子」

- **候选**：IR 里有 `GetProp` / `Call` / `New` / `IterNext`，runtime 极薄。
- **不行**：对象语义要**在每一种宿主语言里各实现一遍**——「一份规范转任意语言」直接退化成
  N 份手工实现，正是本工程要消灭的东西；而且 wasm 侧每个算子都是宿主调用，模块不自洽。
- **采用**：小原语 + `rt_call(id)`。语义仍然只有一份，但它住在 **runtime 的 id 表**里，
  而 runtime 也是 xl 生成的。

### 3.2 让宿主的 GC 管一切

- **候选**：托管宿主里值就是宿主对象引用，不搞句柄表，GC 交给 V8 / .NET。
- **不行**：句柄表/槽数组是**根表**，宿主 GC 看不到 VM 的槽，于是**循环垃圾永远收不掉**；
  堆上限、OOM 语义、挂起帧的可见性在每个宿主上都不一样 ⇒ 安全口径不统一；
  更要命的是它会把**根集错误兜住**——在托管宿主上全绿，到 C++ 上才炸。
- **采用**：判活的权力归 VM（自有 mark-sweep），托管宿主只负责**把载荷的内存还回去**。

### 3.3 引用计数（含「RC + 周期收集器」）

- **候选**：RC 即时回收，内存曲线好看，嵌入式友好。
- **不行**：JS 遍地循环（`a.self = a`、闭包捕自身、原型链环），RC 要么漏、要么再配一个周期收集器
  ——那就是 mark-sweep 加一份计数开销。
- **采用**：直接精确 mark-sweep，不背 RC 的账。

### 3.4 v1 就做压缩 / 分代

- **候选**：一次做对，避免碎片。
- **不行**：移动会让**宿主持有的句柄失效**（宿主把值放进自己的结构体，VM 无权搬它），
  还要引入写屏障与句柄代际检查；而碎片在 v1 的量级上不是瓶颈。
- **采用**：不移动。收益是双重的——句柄稳定 + 无需写屏障（实现简单、易审）。

### 3.5 v1 就做类型特化

- **候选**：`a: number, b: number` 是标注着的，直接生成 `add_f64`。
- **不行**：TS 的类型标注**运行期不成立**（JS 调用方可以传字符串进来），
  而且我们手上是「带类型语法的 AST」而不是「带类型解的 AST」（投影用的是 `ts.createSourceFile`
  那条口径，没有符号表与推断）。按标注生成快路径 = 造出一类「编译器相信了标注」的漏洞面。
- **采用**：v1 只有一个通用加法；特化留到 P4，且必须**带守卫**、语义与通用路径逐值相同。

### 3.6 求值栈式 IL（更贴 wasm）

- **候选**：CIL / JVM / wasm 都是栈机，IR 也用栈，wasm 后端映射更直接。
- **不行**：IR 不可读（差分判据要能 diff）、特化难做、`rt_call` 的参数窗口与 GC 安全点不好定义。
- **采用**：寄存器 + slot，且定死一条：**`rt_call` 的参数与结果都是槽号**——根集于是永远精确。

### 3.7 手动释放或共享所有权（智能指针）

- **候选**：给规范加 `Release()`，或者用共享所有权的智能指针表达 Token 图那样的结构。
- **不行**：脚本侧**不该有释放这个概念**（用户写的 TS 里没有这个东西）；
  共享所有权在带反向指针与环的图上说不清谁该删——所有权信息在规范里根本不存在。
- **采用**：脚本侧没有释放；宿主侧只有一对**有意的**根操作 `Ts_Retain` / `Ts_Release`。

### 3.8 `call` 递归进 `run()`

- **候选**：调用就直接递归跑被调方的指令，代码最省。
- **不行**：递归意味着**宿主栈深度由脚本内容决定**，而宿主栈溢出是**不可捕获的**
  （C++ 撞栈、C# `StackOverflowException` 直接杀进程）。要跑别人的脚本、又要嵌进客户进程，
  这就是一个拒绝服务面。
- **采用**：`call` = 压帧 + `continue`；纯脚本调用**不消耗宿主栈**，
  只有「内建回调进脚本」才消耗一层（由 native 重入深度限制）。

### 3.9 把宿主 async 漏进 VM

- **候选**：`await` 直接映射成宿主的 `async/await`。
- **不行**：客户的 C++ 没有 async 运行时；而且宿主 async 一进来，
  「同 IR + 同输入 = 同输出」这条确定性判据就没了。
- **采用**：微任务队列归 VM，`await` 降级成 `suspend` + 续体。`Ts_Call` 返回前把队列跑干净。

### 3.10 从 NaN-boxing 起步

- **候选**：8 字节值，省内存、贴主流引擎。
- **不行**：需要 f64 ↔ u64 的位重解释，xl 表达不了、也不该表达；
  而「值多大」不是 v1 的瓶颈。
- **采用**：胖联合（`Tag/Int/Dbl/Ref`）。压缩留给各目标在**同一 IR、同一语义**下自行做。

### 3.11 让 id 表吸收语言专有语法糖

- **候选**：`??`、`?.`、`foreach` 各给一个 id，降级期省事。
- **不行**：id 表是**多语言共用的契约**，混进某门语言的语法糖之后，
  下一门语言的 runtime 就得带着上一门语言的残留。
- **采用**：能展开成控制流的都展开（`??`、`?.` 就是控制流 + `rt_get_prop`）；
  id 表**只放语言无关语义**，且只追加、不改号。

## 四、代价如实记

1. **托管宿主上，自有 GC 比宿主 GC 慢。** TS 目标里对象表 + 自有 mark-sweep 一定不如 V8 的
   分代 GC；换来的是**语义与安全口径在所有目标上一致**，以及 wasm / C++ 上不必再写第二套。
2. **胖联合占内存**（16 字节量级）。P4 可以在各目标内自行压缩，契约不动。
3. **每个语义算子一次间接调用**（`rt_call` 的 id 查表）。方案 3.1 的候选在同样位置也有一次 switch，
   所以这不是净亏；真正的优化（内联缓存、特化 op）留在 P4。
4. **不移动 ⇒ 有碎片**。v1 接受。
5. **托管宿主会掩盖根集错误**：TS / C# 上跑绿不代表根集是对的，
   GC 判据必须在 C++ 或 wasm 上过一遍（已写进架构文档 §13）。

## 五、两处存疑（留给以后拍板）

1. **`.d.ts` 作为能力清单**：这条路要等模块与 `declare` 的降级规则落地才能验证；
   如果它不成立，宿主绑定会退回手写注册表（丢掉类型安全那一半收益）。
2. **IR 的紧凑出口**：降级层现在拟以 **TS 形状**为输入（与 `ts.createSourceFile` 逐节点一致的
   那个投影），好处是结构口径已经被 1400 余份语料钉死；代价是投影目前跑在
   `Map<string, any>` / JSON 形状上，会分配。是否给 token 层加一个**同逻辑、不 JSON 化**的
   紧凑 AST 出口，等 P0 的实测数据说话。

## 六、一次量翻又撤回的改法：`JSON.rawJSON` / `JSON.isRawJSON`（第 983 轮）

**结论先写**：这一族**没有落地**，两处尝试都**按实测撤回**，台账原样留着
（`stdlib/json/056-names-json` · `stdlib/json/088-*` · `stdlib/round736/008-*` ·
`stdlib/round751/001-*` 四条仍是 `xl:want differ`）。**下面两件事是量出来的，别重踩。**

### 1. 能力号撞车是**静默走错分支**，不是报错

第一版把两个新号开在 `503` / `504`，理由是仓库里那句「`500` 那一段只有 `501..503`」——
**那句话是错的**：`503` 是 `DateToJSON`、`504` 是 `ObjectToLocaleString`
（`globals.xl.md` 的 `# const` 段一眼可见）。撞号的症状不是编译错，是
`JSON.stringify(new Date())` 走进 `503`、于是 `Date.prototype.toJSON` 那一次调用落进
**新函数**、交出一个布尔 ⇒ 实测**当场红 15 条**（`stdlib/date/041` 一族 5 条 blocked、
`stdlib/json/*` 10 条 differ），其中一条把 Date 印成 `{"d":d}`。

**可复用的判据**：加能力号之前**先把那一段 `# const … :int = N` 全量列出来**对一遍
（一行 Node 正则就够），不要相信任何一句散文里的「空着」。

### 2. 判定层能表达的「内部」只有 `PropertyFlagInternal`，而那与属性名判据不同源

`JSON.rawJSON` 在规范里造的是一个带**内部槽** `[[IsRawJSON]]` 的普通对象，
`JSON.stringify` / `JSON.isRawJSON` 按那个槽认。本层能表达「脚本看不见」的只有
`SetHiddenProperty` + `FindProperty(…, true)` 那一格，所以能造出来。
**但第二版仍然没能落地**：`JsonText` 是 `JSON.stringify` 递归里**每一格**都过的地方，
多出来的那几次键字符串分配把回收时机推到了另一处 ⇒
`runtime:check` 的「语言层手里的中间数组要有根」那一条当场红
（`[...一个 3 千项的 Symbol.iterator]` 里的 `Array.from` 抛 `the script threw`），
**加了 `IsObject()` 早挡之后仍然红**。

**这一条留给以后**：要动它就得连**根集那一族判据**一起量
（`tests/runtime/check.mjs` 第 199 / 200 轮那两条是**阈值敏感**的：递归里多几次分配就换一处回收点）。
**不要**把它当成「挂两个名字」的小活。
