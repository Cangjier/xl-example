# BufferSize 扫描（8 / 16 / 32 / 64 / 128，含 256 参照）

> 目标：buffer 驱动重构后，`SyntaxContext` 一次处理一个窗口 `[Index, Index + BufferSize)`（默认 32）。
> 本文件回答两件事：**窗口大小对耗时的影响有多大**，以及**窗口大小会不会改变语义**。
> 本轮**只做测量**：`core` / `typescript` 一行未改，新增的只有 `tests/bench/buffer-size-sweep.mjs` 与本文件。

## 0. 结论摘要（TL;DR）

1. **窗口大小对总耗时的影响很小，量级 1%–4%**。以 `size=32` 为参照（三次独立会话的 Δ% 均值）：
   `8 → +3.67%`、`16 → +0.80%`、`32 → 0`、`64 → −0.48%`、`128 → −1.24%`、`256 → −1.46%（单次）`。
   **32 之后基本平坦**，再放大窗口最多再省 ~1.5%；缩到 8 则要付 ~3.7% 的代价。
2. **语义完全不变**：4497 个可解析文件 × 6 个窗口大小，`Root.ToString()` 的 UTF-8 字节流**逐字节相同**
   （每个 size 都是 34,046,403 B，无一处差异）；另有 9 个文件在**所有** size 下抛同一个错（同错，不是窗口引进的）。
3. **推荐保持 `BufferSize = 32`**：64/128 的收益（−0.5% / −1.2%）落在 3% 噪声带内，虽然三次会话符号一致、
   说明效应真实存在，但幅度不足以支撑改动一个已被验收的常量；8 明显更慢，说明"把窗口调小以省内存"是有代价的。
4. **机制上可以解释**：窗口大小只改变 `Root.Process` 的**调度次数**（每窗口一次），每多一次窗口约 0.2–0.3 µs；
   8 比 32 多 65.6 万个窗口，实测多 109–151 ms，一阶反推 166–230 ns/窗口。真正的成本仍在每字符的 token 链上
   （32 时 **533 ns/字符**），不在窗口边界。

## 2. 方法

### 2.1 为什么手工装配

`SourceFileRunner.Parse` 里 `new SyntaxContext(root)` 固定走默认 32，要扫别的窗口只能按 runner 的装配自己拼。
顺序与 runner 完全一致，唯一差别就是那个 `bufferSize`：

```js
const template = TypescriptTemplate.Create();
const root = new SourceFileShape(template);
const context = new SyntaxContext(root, size);   // ← Parse 里这里是 (root)
context.Process(new TextDocument(text, filePath));
```

因此**任何耗时差异都只能来自窗口大小**：模板、根单元、驱动顺序、`Process` 主循环都是同一份代码。

### 2.2 为什么同进程、逐轮交替

- **同进程**：跨进程跑会把 JIT 预热程度、页缓存、CPU 频率的差异算到 size 头上。
- **交替**：每轮对每个文件把**所有 size 各跑一次**，顺序按 `(轮次 + 文件序号) % size 数` 轮转、奇数轮整体反向。
  这样每个 size 在"第一个跑 / 最后一个跑"的位置上出现次数相同，抵消"越跑越热"的位置偏置。
- **中位数**：每轮每个 (文件, size) 一个样本，repeat=5 后取中位数，TOTAL 是各文件中位数之和
  （与 `tests/bench/buffer-ab.mjs` 同一口径，便于互相引用）。

### 2.3 语料

| 组 | 文件 | 字符 | 说明 |
| --- | --- | --- | --- |
| `lib/*.d.ts` | 8 | 4,056,011 | 最大 8 份（`lib.dom.d.ts` 2.35 MB，独占该组 58%），与 `parse-perf` / `buffer-ab` 同一批 |
| `tests/cases` | 4487 | 2,936,930 | 真实 `.ts` 用例，短文件多（每文件固定开销占比高） |
| `samples` | 2 | 1,922 | 仓库自带样例（`samples/generic.ts` 本身语法错误，被预筛剔除） |

`typescript/cases` **没有进默认语料**：那里是模板化用例，行内 `\n` 是等待 `ast-json.mjs` 还原的转义文本，
直接喂 parser 会抛错（53 个里只有 9 个可解析），不适合当计时语料。需要时 `--corpus typescript/cases` 显式指定。

预筛：先按参照 size 解析一遍，抛错的文件不进计时（错误路径的耗时与正常路径不可比），
但它们仍参加 XML 等价性检查——要求"在所有 size 下抛同一个错"。

### 2.4 输出口径

- `TOTAL`：各文件中位数之和（ms）。
- `Δ%`：`(TOTAL(size) − TOTAL(32)) / TOTAL(32) × 100`，正数 = 更慢。
- `ns/字符`：`TOTAL × 1e6 / 语料字符数`。
- `轮间极差%`：该 size 的 5 个"每轮合计"里 `(max − min) / median`，是 TOTAL 级的稳定性指标。

### 2.5 等价性通道

对每个文件、每个 size 解析一次（**不计时**，单独一遍），取 `Root.ToString()` 转 UTF-8 字节，
与 `size=32` 的字节流逐字节比较；不等价时打印首个不同字节的位置与两侧上下文。
参照 size 自己就抛错的文件，比较"其它 size 是否抛同一个错"。

## 4. 曲线

Δ% 相对 size=32（三次会话均值；柱长 = |Δ%| × 10 格）：

```
  8    +3.67%  ████████████████████████████████████▏
 16    +0.80%  ████████▏
 32     0      ·
 64    -0.48%  ████▊
128    -1.24%  ████████████▍
256    -1.46%  ██████████████▌        （单次会话 C）
                        ┊ -3% 噪声带边界在两侧 30 格外
```

形状是**单调下降后饱和**：窗口越大越省，32 之后每翻一倍只再省 ~0.2%–0.7%，128 之后基本不动。
8 是唯一明确跑出噪声带的点（+3.7%，三次会话都为正）。

### 4.1 机制：每多一个窗口 ≈ 0.2–0.3 µs

窗口大小只改变 `SyntaxContext.Process` 里 `Root.Process(this, buffer, index)` 的调用次数：

| size | 窗口数（≈ 6,994,863 / size） | 相对 32 的窗口数差 | 实测 Δms（A / B / C） | 一阶反推 ns/窗口 |
| ---: | ---: | ---: | ---: | ---: |
| 8 | 874,358 | +655,768 | +108.7 / +148.8 / +150.7 | 166 / 227 / 230 |
| 16 | 437,179 | +218,589 | +25.6 / +29.9 / +33.4 | 117 / 137 / 153 |
| 32 | 218,590 | 0 | 0 | — |
| 64 | 109,295 | −109,295 | +7.2 / −42.0 / −17.8 | 符号不稳，忽略 |
| 128 | 54,647 | −163,943 | −55.2 / −35.7 / −47.0 | 336 / 218 / 287 |
| 256 | 27,323 | −191,267 | −53.9（C） | 282 |

8 侧反推 0.17–0.23 µs、128 侧反推 0.22–0.34 µs，同一量级 → **窗口调度本身约 0.2–0.3 µs/次**，
两端数据互相印证。按这个价目，8→32 应省 109–151 ms（实测 109–151 ms），32→128 应省 33–49 ms（实测 36–55 ms），
模型与实测在误差内一致。**结论：窗口大小只影响这一次调度，不改每字符的 token 处理成本。**

## 5. 噪声说明

- **TOTAL 级**：5 轮"每轮合计"的极差 1.6%–5.6%（A：1.60/2.23/3.07/2.68/2.04；B：5.67/3.81/3.20/4.65/3.94）。
  这是 4497 个文件、~100 秒的整轮抖动，主要来自 GC 与 CPU 频率。
- **逐文件级**：单个 (文件, size) 的轮内极差中位数 23%–28%、P90 74%–87%——绝大多数文件只有 0.05–0.5 ms，
  单个文件的百分比没有意义；**中位数 + 全量求和**才把它压到 TOTAL 级的 2%–6%。
- **跨会话**：同一配置三次会话，32 的 TOTAL 是 3731 / 3680 / 3702 ms（±0.7%），8 是 3840 / 3829 / 3853 ms（±0.3%）。
- **判据**：单次差异 < 3% 视为噪声。按此，`16 / 64 / 128 / 256` 相对 32 全部在噪声带内；
  `8` 的 +2.91%（A）压线、+4.04%（B）/+4.07%（C）出带，三次**同号**，因此认为"8 确实更慢约 3.7%"成立，
  但幅度只能报到"~4% 量级"，不能报到小数点后两位。
- **符号一致性比单次幅度更可信**：32→128 的三次 Δ 分别是 −1.48 / −0.97 / −1.27，全部为负——效应真实但很小。
- 没有用 profiler 计时；没有做 CPU 绑核、没有关超线程；没有跨机复现。

## 6. 推荐值：保持 `BufferSize = 32`

理由，按权重排序：

1. **收益不足**：64 / 128 相对 32 的收益是 −0.5% / −1.2%，都落在 3% 噪声带内。虽然三次会话符号一致
   （说明效应真实），但 1% 量级不足以支撑改一个已通过验收的默认常量，尤其是 `SourceFileRunner.Parse`
   也把 32 写死、常量一改就要同步两处。
2. **32 已在平台段**：128 → 256 只再快 0.19%，说明曲线在 64–128 之间就平了；继续放大只是把窗口做粗，
   换不到可测的收益。
3. **不要往下调**：8 比 32 慢 3.7%（三次一致），相当于 7M 字符多 109–151 ms。
   如果将来为了内存把窗口调小，代价就是这个量级——"窗口小一点更省内存"在时间上不是免费的。
4. **如果非要选一个更快的**：`128` 是（−1.0% ~ −1.5%，三次同号），`256` 没有额外收益。
   落地前建议把 repeat 提到 9 或换机器复现一次，确认 −1% 不是这台机器的特性。

一句话：**当前默认 32 是合理值；窗口大小不是这条流水线的性能杠杆（杠杆在每字符 533 ns 的 token 链上）。**

## 7. XML 逐字节等价结论

```
XML 逐字节等价：PASS 4497 / FAIL 0 / ERROR 0 / 同错 9
（基线 size=32，共 4506 个文件 × 5 个 size；会话 C 为 6 个 size）
各 size 的 XML 字节总量：s8=34046403B  s16=34046403B  s32=34046403B  s64=34046403B  s128=34046403B
结论: 窗口大小不改变语义（8/16/32/64/128 的 XML 全部逐字节相同）。
```

- 4497 个可解析文件 × 每个 size 的 `Root.ToString()` UTF-8 字节流与 `size=32` **逐字节相同**，
  每个 size 的字节总量都是 **34,046,403 B**（会话 C 的 256 同样相同）。
- 9 个文件（`samples/generic.ts` 与 8 个 `tests/cases` 用例）在参照 size 下就解析失败，
  它们在所有 size 下**抛同一个错**（消息逐字相同），故计为"同错"，不算不等价。
- 这条通道覆盖的是 **XML 产出**（与 cjcli 写出的 XML 同源）；XML 不含位置，所以它证明的是"语义产出不变"，
  不证明 `SourceRange` 的中间坐标过程逐位相同。位置通道的等价性由 `tests/bench/buffer-equivalence.mjs --mode digest`
  在基线/实验两版 build 之间另行验收，本扫描不重复。

## 9. 限制

- 单机、单进程、单次构建（`integration-buffer@f5a525c3`）；换 CPU / 换 Node 版本，绝对值会变，
  但"32 之后平坦、8 更慢"的形状应当稳定。
- 语料偏 d.ts：`lib.dom.d.ts` 一个文件占 34% 字符，`lib/*.d.ts` 整组占 42% 时间；短文件组（4487 个 `tests/cases`）的
  每字符成本（~733 ns/char）显著高于 d.ts（~388 ns/char），因为每文件都有固定的建模板/建根开销。
  真实工程的混合比例不同，绝对值不能外推。
- 合成档样本太小（26k 字符），只能证伪不能证明；1% 级结论只用全量语料。
- 没有测量内存占用与 GC 次数随窗口大小的变化——本任务只问耗时与语义。
