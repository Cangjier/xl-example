## 1. 结论先行

D5 §2.1 说 A 类 13 条「吞」的首因在**收口**，方向对，但**落点不是终点判据，而是「什么时候收口」这一拍还在不在飞**：

- 13 条里 **5 条**（全部是解构绑定 `let/const { … } = …`）的共同机制是：`{ … }` 这个绑定括号**闭合的那一拍**
  `Bracket.Close → 父目录 ComputePossibleShapes → VariableStatementPossibleShape.Accept` 建出三层链，
  而**括号自己的 `UnitToken.Process` 循环仍在栈上**。旧代码为了保住刚挂好的挂载链，
  把括号的 `Parent` 置成 `null`（`[WP-A6c]`），于是循环顶部的退出守卫
  `parent !== null && parent.MountedUnit !== this` **永远不成立**，括号把后面所有字符（下一条语句整条）
  `Add` 进已经关闭的自己。根层于是少一整条 `const` / `let`。
- 换成「挂到自己的 binding-pattern 形状上」之后：`Quit()` 仍然无害（pattern 的 `MountedUnit` 恒为 `null`），
  而守卫立刻成立 ⇒ 循环退出 ⇒ 字符回到父单元，由刚挂好的 statement → list → declaration 链接手。
- 这一改动**顺带**救回 29 条同类差异（`decl-*destructure*` 族、`gap-sweep-*-destr-*` 族），
  因为同一只指针在整个解构族上都成立。**13 条里 5 条转 PASS，差异总数 −34。**

**目标对照**：差异 88 → **54**（目标 ≤75，超目标 21 条）；崩溃 20 不变；fallback 总数不变；
0 条「原来通过现在失败」。**但 13 条只清掉 5 条**，剩余 8 条各自的卡点见 §4，没有把「少几条」当完成。

## 2. 改动（唯一一处）

`typescript/tokens/declarations/variable-declaration-possible-shape.xl.md` · `IncrementalVariableStatementBuilder.Build` 末尾：

```ts
if (binding instanceof Bracket) {
  // [WP-A6c] Build runs at the closing bracket tick; Bracket.ExitOrPre calls Quit() right after
  // TryToClose, and Quit() clears Parent.MountedUnit - that would detach the statement we just mounted.
  // Re-parenting the bracket onto its own binding-pattern shape makes that Quit() write to the pattern
  // (whose `MountedUnit` is always null) instead of to the host, so the mount chain survives.
  //
  // **[W1:BRACKET-LOOP] 不能写成 `Parent = null`**：在飞循环的退出守卫是
  // 「`parent !== null && parent.MountedUnit !== this`」。`Parent = null` 让这条守卫永远不成立，
  // 于是括号的循环继续吃下一行的字符（实测 `bracket.Data` 多出 `= obj ⏎ let …`）。
  const bracketBinding = binding as Bracket;
  if (pattern !== null) {
    bracketBinding.Parent = pattern;
  } else {
    bracketBinding.Parent = null;
  }
}
```

- **为什么改在这里**：Build 是三层链的唯一建造点，`binding instanceof Bracket` 那一支正是「解构绑定」；
  缺陷是这一支自己留下的挂载状态，不是终点判据算错了（终点判据在 `;` / EOF / 行尾都答得对）。
- **写域说明**：D5 §4 给 W1 的写域是 `variable-declaration-end-possible-shape`（终点判据）+
  `variable-declaration-list-possible-shape`（收口时清在飞循环）。实测首因在两者的上游——
  `variable-declaration-possible-shape` 的 `IncrementalVariableStatementBuilder.Build`
  （三层链建造点，D5 §4 未点名，也不属于 W2/W3/W4 的写域）。**没有碰** `statement-possible-shape`（W2）、
  `statement-builder`（W3）、`wide-ast`（W4）；`variable-declaration-end-possible-shape` 与
  `variable-declaration-list-possible-shape` 一个字节未改。
- **开关**：`VariableStatementPossibleShape.BuildByIndex` 只在
  `StatementRouteUtil.IsIncrementalVariableShapesEnabled()` 为真时调用本函数，默认 `false` 时这一行不执行。
