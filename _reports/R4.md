## 1. trivia：把 `left..operator` 那段搬进 `binary.Data`

**根因**：`BuildByIndex` 只做两次 splice（摘运算符、摘左操作数、插 `Binary`）。夹在
`leftIndex..tokenIndex` 之间的 `WrapSymbol [11,12)` 既不属于左操作数、也不属于运算符，于是留在宿主里，
并且被插到 `Binary` **后面**——树里顺序与源码相反。`host.MountedUnit = binary` 只能接住**之后**到达的
单元（`[13,14)` 因此进得去），接不住已经落在宿主里的 `[11,12)`。

**改法（通用）**：

- `ItemUtil.TriviaBetween(units, leftIndex, tokenIndex)`：取两格之间按源码顺序的 trivia；
- `ItemUtil.InsertTrivia(node, at, trivia)`：按顺序插进 `node.Data` 并设 `Parent`；
- `BinaryExpressionShape.FromLeftAndOperator(..., trivia?)` 新增可选参数：`Add(left)` →
  `Add(trivia…)` → `Add(operator)`，省略时与旧行为逐字相同；
- `BinaryExpressionPossibleShape.BuildByIndex`、`BinaryOperatorPossibleShape.BuildByIndex`、
  `ReassociationPossibleShape.BuildByIndex` 都改成 `splice(leftIndex, 1, binary)` +
  `splice(leftIndex + 1, trivia.length)`，先把 trivia 从宿主摘掉再建；
- 三处的 `Parent` 全部由 `Add` / `InsertTrivia` 设成 `binary`；`left` / `operator` 的既有 `Parent`
  处理（`Add` / `Replace`）一个字没动。

**再结合拆层**（`Reassociate`）：旧 `Binary.Data` 现在可能含 trivia，所以不再要求「正好三格」，而是按
**代码单元**拆成左操作数 / 运算符 / 右操作数，另收两段 trivia：

- `outerTrivia`（左操作数..旧运算符）挂回重建外层的 left 之后；
- `newTrivia`（旧左 `Binary`..新运算符，来自宿主）挂进**新内层**的 left 之后；
- `innerTrivia`（旧运算符..右操作数，正常已被 `RightOperandPossibleShape` 摘掉）若存在则挂在外层
  运算符之后，不丢数据。

## 2. 再结合：从 `*` / `+` 扩到全部二元运算符

**判据只有一处**：`BinaryExpressionShape.NeedsReassociation(left, precedence, text)`：

1. 左操作数不是 `BinaryExpressionShape` ⇒ 不拆；
2. 左 `Binary.OperatorPrecedence < 0` ⇒ 不拆；
3. `left < precedence` ⇒ 拆（`1+2*3`）；
4. 同优先级且 `OperatorTable.IsRightAssociative(text)` ⇒ 拆（`a**b**c`）；同优先级左结合**不拆**
   （`1+2+3` 仍走常规原位长外层）。

`OperatorTable` 是唯一优先级表：本判据只读 `Precedence` / `IsRightAssociative`，没有硬编码 14/13。

**两个候选怎么分工（同格不能双 Accept）**：

- `ReassociationPossibleShape.ComputeByIndex`：`*` / `+` 无条件 `Accept`（既有独占）；**其余任意二元运算符**
  （含 `in` / `instanceof`）只在 `NeedsReassociation` 成立时 `Accept`；
- `BinaryOperatorPossibleShape.ComputeByIndex`：原有的常规格判据全部保留（`=` / `<` 类型实参 /
  除号就地物化 / 左操作数），只在 `NeedsReassociation` 成立时 `Reject` 让路；
- `BinaryExpressionPossibleShape` 的 `Accept` 集合不动（它只接「左操作数还不是形状」的格，仍是原来的
  显式拒绝路径）。

**`BuildByIndex` / `BuildOperator`**：

- `ReassociationPossibleShape.BuildByIndex` 不再对 `text !== "*" && text !== "+"` 抛错；左操作数不是形状时
  走 `BinaryOperatorPossibleShape.Operand`（同一个就地物化入口，不复制第二份）；
- `BuildOperator` 一律走 `OperatorShapeMap.Create(text, PositionBinary, …)`，`*` / `+` / `|` / `&` / `==` /
  `<<` / `&&` / `??` / `in` / `instanceof` 全覆盖，本文件不再维护第二份「文本 → 类」表；
- 常规路径的运算符 `Pos` 仍是 `IncrementalItemPosition.AfterPreviousCode`（C1），
  再结合路径由 `ShapeOperatorStack` 的 `CheckOperatorPos` 校验。

**顺带的两处必要收窄**（否则 `a == b < c` / `a != b < c` / `a ?? b ?? c` 的**左操作数根本不物化**）：

- `PrimaryAtomGuard.IsTerminalAfter`：两字符运算符的首字符（`==` `===` `!=` `!==` `??`）也算续接；
  单个 `=`（赋值）/ `!`（前缀、非空）/ `?`（条件）仍然排除。`ContinuationChars` 字段未改。
- `MemberChainJudge.ChainFollows`：`!` 后紧跟 `=`、`?` 后紧跟 `?` 不算成员链后缀（那是 `!=` / `??`，
  不是 `a!` / `a?.`）。否则 `MemberAccess` / `ElementAccess` / `OptionalChain` 在链头格上一直
  `Uncertain`，A1 永远拿不到唯一候选，`!=` / `??` 只能退回 EOF 原子建树。
