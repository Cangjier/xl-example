## 3. 首因：不是「类型字面量被放弃」，是**别名壳提前收口**

两件都不是 TypeBuilder 的类型文法缺格（`-1` / 泛型函数类型本来就是好用的），而是 B4c 新加的
`TypeAliasDeclarationShape.ComputeEndIndex` 把**别名收在了错的格**上，交出去的「类型槽」只剩半截：

| 文件（出事的那条语句） | 收口格 | 交给 `FromUnits` 的类型槽 |
|---|---|---|
| `type U = <U>` ⏎ `(a: U) => U;` | `>`（配对 `<U>` 那个） | `<` `U` `>` → `ParseGenericFunctionType` 等不到 `(` ⇒ **泛型函数类型缺少参数表** |
| `type U = -` `//c` ⏎ `2;` | `-` | `-` → `ParsePrimaryType` 找不到数字 ⇒ **负数字面量类型缺少数字** |

两条都是 `CanEndType` 把「不可能收一条类型」的单元当成了结束格：

1. `CanEndType(Symbol "-")` 返回 **true**（`-` / `+` 只出现在映射类型修饰词与符号字面量前缀里，
   它们自己从来收不了一条类型），于是「下一行首词 `2` 与前一个代码单元 `-` 之间隔着行终止符」
   那条分支（`ComputeEndIndex` 末尾）把别名收在 `-` 上。
2. `CanEndType(Symbol ">")` 返回 true 本身没错（`Array<T>` 就该收在 `>`），错的是
   `<T>` 是**泛型函数类型的类型参数表**：它后面必须还有 `( … ) => …`。第一条修复只挡住了 `last`
   这一个候选格，实测收口改从另一条分支的 `previous` 走（`leading` 是新建的 `(` 括号、
   `UnitText(Bracket)` 为 `""` ⇒ `IsNewLineContinuation("")` 为 false），所以第二处必须同口径。

诊断证据（`tmp/probe-endindex.mjs` / `tmp/probe-fununits.mjs` / `tmp/probe-generic-head.mjs`，
均只读、不入库）：包一层 `ComputeEndIndex` 打印每次 `>= 0` 的收口与 `Data` 尾部，就能看到
`CLOSE atEof=false end=9/12 tail=Common("U") Symbol(">") WrapSymbol("\n") Bracket("(")`。

## 4. 修法（`type-alias-declaration-shape.xl.md`，三处，全部只判结构位）

1. `## static method CanEndAtType:(data, index)=>bool`（新）——**结束格候选的统一口径**：
   `CanEndType` 且不是泛型函数类型头的配对 `>`。`ComputeEndIndex` 的 `last` 与「下一行首词」分支的
   `previous` **都只问这一句**，不再两处各判一套。
2. `## static method IsGenericHeadClose:(data, last)=>bool`（新）——从 `last` 的 `>` 向前找配对的 `<`；
   只有当那个 `<` 前面**没有类型代码**（前面是 `=` 或槽首）时才是「泛型函数类型头」。
   `Array<T>` / `Map<K, V>` 的 `<` 前面有标识符 ⇒ 不受影响（`type A = Array<T>` ⏎ `const x = 1`
   的分句行为逐字不变）。
3. `CanEndType`：`Symbol` 分支补 `-` / `+` 两个不可收口项（注释写明来历）。

**为什么不是「让 TypeBuilder 也吃注释」**：类型槽被截断的根因在收口，不在建树；在 `ParsePrimaryType`
里补「跳过注释」只会把 `-/*c*/1` 收进来，但 `<U>` ⏎ `(a: U) => U` 那件仍然缺参数表，
而且会把两份类型文法各改一处。修在收口上，两件一起回到 legacy 原本的建树路径（`FromUnits`），
`xl:expect` 的 `LiteralType / AreaAnnotation / LineAnnotation / TypeParameter / FunctionType` 计数
一个没动（`cases:check` 1720 条 0 不合格、两件用例 AST 与 TS 逐节点一致）。

## 6. 没做的那一半：`type U = A | B` / `type F = (x: number) => void`

**只记录，不动**（本轮到了回合上限，且按目标 5 的「不增加 diff/fallback 才能推进」这条前置没验完）。
现状与下一步（下一棒可直接照做）：

- 两者今天都**已经**走早壳收口、由 legacy `ParseUnionType` / `ParseFunctionType` 一次建出，
  AST 与 TS 一致（`type-union-leading-bar.ts` / `type-fn-*` 均不在 33 件差异清单里）——
  缺的只是「联合成员 / 形参表在**闭合格就地**成形」的那一格账本，不是正确性。
- 推进时必须复用本轮的 `CanEndAtType`：联合成员 `type U = A |` ⏎ `B` 的候选格是 `|`
  （`CanEndType("|")` 已为 false，安全），而 `type F = (x: number) =>` ⏎ `void` 的候选格是 `=>`
  （亦已为 false）；**别**再让 `-` / `>` / `(` 这类「看着像结束格」的单元混进来。
- 判据顺序建议：先只开「联合成员闭合格成形」，跑 `wide-ast` 默认档看 33 件清单是否仍逐字相同、
  fallback 是否仍 ≤ 84；绿了再开函数类型形参表。任一步出现新差异或新 fallback ⇒ 退回本节只记录。
