**一句话**：5 条非 lib 崩溃（B3 2 条 + B4 3 条）的**崩溃点**是同一个：`SourceFileEndPossibleShape.BuildByIndex`
尾段的两次建树尝试（`BuildTrailingDeclaration` / `BuildStatementSegments`）都会就地 `splice`，
失败后 `start` / `at` 已经过期；旧代码拿过期下标继续调 `ExpressionStatementShape.FromUnits`，
读到 `host.Data[at] === undefined` ⇒ `TypeError: Cannot read properties of undefined (reading 'IsTriviaToken')`。
修法：尾段每一轮都**按当前 `Data` 重新定位**，成功一次继续下一轮，数组不再变化才走最后一条兜底；
两条尝试的先后与判据一个字不改。**不是**关开关、不是吞掉首跳错误、不是把崩溃改成崩溃计数。

`_reports/D5-triage.md` 在 `xl-example/_reports` 下**不存在**；它在 `xl-example-set/_reports/D5-triage.md`
（共享报告目录）。本波按 W3 §1.1 的逐条表与现场实测取数，未依赖该文件的新结论。

## 2. 逐条现场：两个子族的**首跳**确实不同，但崩溃是同一个

`tmp/w6min.mjs`（同一次 `ParseCore` 分三档：ON = shell + 两开关、OFF = shell 关增量、LEGACY = legacy 两开关）。
5 条都是 **OFF 通过、ON 失败、LEGACY 崩**；wide 看到的崩溃是「ON 抛错 → 文件级 fallback → legacy 再崩」的那一次。

| 文件 | ON（首跳）报错 | LEGACY（次跳，崩溃点） |
| --- | --- | --- |
| `expr-as-then-value-operator` | `增量变量形状未支持：declaration 初始化器根之外的运算符`（`const eq = a as number === 1;`） | `undefined.IsTriviaToken` |
| `expr-as-type-nonnull-tail` | `增量变量形状未支持：declaration 符号 !`（`as T!`） | 同上 |
| `gap-as-bang-array-type` | 同上（`as T![]`） | 同上 |
| `expr-r1233-control-head-regex` | `没有候选形状可以构成（宿主 ConditionalExpressionShape，下标 3）`——**不是**行首 `/`，是 `const v5 = a ? (a) : (a)` 这个**括号分支的三目** | 同上 |
| `expr-r1234-bare-block-regex` | `增量变量形状未支持：declaration 符号 /`（`const v1 = { p: 1 }` ⏎ `/re/g;`，TS 是除法续接） | 同上 |

两个子族的语法点（`as T!` 的类型位后置 `!` / 裸块与对象字面量后的行首 `/`）都在**首跳**里，
各自是一条独立的增量形状缺口；但它们能变成「崩溃」而不是「fallback 后差异」，只因为次跳
`BuildByIndex` 的尾段兜底用了过期下标。本波修的是**这个共同的崩溃机制**，不是把两个子族当成同一个 bug。

### 崩溃机理（`tmp/w6trace.mjs` / `tmp/w6legacy.mjs` 实测）

以 `gap-as-bang-array-type` 的最小片段为例（`declare const f: any;` ⏎ `type T = any;` ⏎ `const q = f() as T![];`）：

```
BuildByIndex(tokenIndex=53, len=54)
  BuildStatementSegments(0,26) -> true   len 54=>28   # 成功建出前两条，Data 变短
  BuildTrailingDeclaration(2,9) THREW 类型别名声明的类型没有读完   len 28=>29
  BuildTrailingDeclaration(0,35) THREW ...            len 54=>29   # 下标 35 已不属于当前数组
  BuildTrailingDeclaration(0,51) THREW ...            len 54=>29
  BuildTrailingDeclaration(0,51) THREW undefined.IsTriviaToken
  BuildStatementSegments(0,51) THREW 语句没有读完…
```

`len 54=>29` 与 `at=35/51` 并存就是「过期下标」的直接证据：`BuildTrailingDeclaration` 在失败前会先插一个
零宽合成 `;`，数组形状已经变了；旧代码把进入方法时抓下的 `at` 一直用到最后一次 `FromUnits`。
`declare const` 只是让 W3 那一步把尾段留到 EOF 的条件；真正被杀的是**失败尝试之后继续用旧下标**。

## 3. 改动（唯一一处）

`source-file-end-possible-shape.xl.md`：

1. 新增 `static method LastCodeIndex:(host)=>int`——在**当前** `host.Data` 上取「最后一个代码单元」，
   与 `ItemUtil.ItemStart` 配对，替代进入 `BuildByIndex` 时抓下的 `start` / `at`。
2. `BuildByIndex` 的尾段兜底改成**带重新定位的循环**：

```ts
let advanced = false;
let previousLength = -1;
for (let round = 0; round < 8 && host.Data.length !== previousLength; round++) {
  previousLength = host.Data.length;
  const roundStart = ItemUtil.ItemStart(host.Data);
  const roundAt = SourceFileEndPossibleShape.LastCodeIndex(host);
  // …按当前范围依次试 BuildTrailingDeclaration → BuildStatementSegments…
  if (host.Data.length !== previousLength) { advanced = true; }
}
// 最后一条 ExpressionStatement 兜底同样按当前范围取；建不出来交给 EOF 收尾（不抛）
```

- **判据不变**：仍然是「先 `BuildTrailingDeclaration`，不行再 `BuildStatementSegments`，最后单条
  `ExpressionStatement`」；`;` 走 `requireSemicolon` 分支、`IsStandaloneTrailingStatement` 等分支一个字未动。
- **退出条件**只看数组长度有没有变化（= 这一轮至少建出一条语句），最多 8 轮，病态输入不会打转。
- **最后一条兜底**失败时不再抛错，留给 EOF 收尾（与既有的 `IncrementalStuckShellRecovery.CountEofLeftover`
  同一条「未认领的尾单元在 EOF 丢弃」口径）。走到这里已经证明它不是任何已知语句形态，
  抛错只会把整份文件打成崩溃；这是尾段兜底「能建几条建几条」的既有语义，不是新开的口子。

为什么不是「按两个子族各写一条特判」：首跳的两处缺口（`as T!` 的类型位 `!`、`(a) ? :` 括号分支）
在增量形状层各自是独立 WP，本波**没有**动它们；但它们触发的是同一条次跳崩溃，修次跳的过期下标
同时消掉两个子族、且不改变任何首跳判据——用一条机制修复代替两条特判，行为更窄、可解释性更强。
如果以后首跳补上，这两条会直接从 crash→OK，不需要再改这里。
