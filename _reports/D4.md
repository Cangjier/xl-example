## 2. 根因与改动（`ParseCore`）

`ParseCore(text, filePath, shell)` 原来只做 `EnableShellExpressions = shell` 的临时切换
（`typescript/run/source-file-runner.xl.md`）。而 legacy 候选目录不止这一个开关：

- `EnableIncrementalVariableShapes`（变量声明族，`IsIncrementalVariableShapesEnabled()`）与
  `EnableShellExpressions` **相互独立**（`statement-route-util.xl.md` 的字段说明写明了两两独立）；
- `EnableIncrementalShapes`（全场景一级开关）同样独立，声明挂载 / 块体 / 控制流 / 表达式体都读它。

于是 `shell=false` 的第二跳只换了外壳：变量声明族仍走增量目录，D3b §3 实测第二跳在原地复现同一条
`CatalogGuide` 异常。改动就一行语义：**`shell=false` 时把这两个增量开关一起压成 `false`，并在同一个
`finally` 里恢复**（三个开关都恢复，调用方看到的开关值与本方法调用前逐位相同）。

```ts
if (!shell) {
  StatementRouteUtil.EnableIncrementalVariableShapes = false;
  StatementRouteUtil.EnableIncrementalShapes = false;
}
// try { 模板 → 根 → 上下文 → 跑一遍 } finally { 三个开关全部恢复 }
```

**恢复不是口头保证**（`tmp/switchcheck.mjs`，`EnableIncrementalShapes/VariableShapes` 先置 `true` 再 `Parse`）：

```
{"file":"let-const-statement-shell.ts","outcome":"ok","lastFileFallback":true,
 "after":{"shell":true,"variable":true,"incremental":true}}
{"file":"type-return-abstract-new.ts","outcome":"ok","lastFileFallback":true,
 "after":{"shell":true,"variable":true,"incremental":true}}
```

两条都走了 fallback（`lastFileFallback:true`），调用方拿回来的三个开关仍是 `true`。

### 2.1 「两个都压」是量出来的，不是顺手（三配置同语料实测）

| fallback 里压哪些开关 | 崩溃 | 有差异 | 救回 | `ok→diff` |
| --- | --- | --- | --- | --- |
| 一个都不压（= 改前） | 104 | 104 | 135 | — |
| 只压 `EnableIncrementalVariableShapes` | 32 | **107** | 207 | 2 |
| **两个都压（本提交）** | **26** | **103** | **213** | 2 |

只压变量声明族：diff 反而 **+3**（107 > 104），少救 6 条。两个都压才同时把崩溃和差异都压下去。
两条 `ok→diff` 在两种配置里**完全一样**（见 §5），所以它们不是「压多了」造成的。

## 4. fallback 成功后 AST 对不对（逐文件）

- 213 条救回里 **211 条与 TS 逐节点一致**（`fallbackSavedDiff = 2`）。
- 2 条不一致，且**全部**是 `ok→diff`（改前靠泄漏版 fallback 通过，改后 legacy fallback 给出另一棵树）。
- 26 条仍失败里没有任何「错树」——它们是硬抛错，没进 AST 对拍。

### 4.1 两条 `ok→diff` 的最小复现与归因（`tmp/attr.mjs`，`ParseCore(false)` 直跑）

| 最小片段 | legacy（shell=false 且两个增量开关 false） | shell+incremental |
| --- | --- | --- |
| `const o = { *m() { yield 3; } };` | `ExpressionStatement+1, YieldExpression-1, NumericLiteral-1` | OK |
| `const o = { *m() { return 3; } };` | `ReturnStatement-1, NumericLiteral-1` | OK |
| `const arrow = () => /* { */ { return 3; };` | `ReturnStatement-1, NumericLiteral-1` | OK |
| `const arrow = async () => await 1;` | OK | OK |

⇒ 两处都是**变量初始化器里的原子建树**丢东西：对象字面量的生成器 / 异步方法体、注释括号箭头体，
legacy 丢 `return` / `yield`，而增量初始化器目录建得对。落到两个文件上正是同一格：

| 文件 | 差 | 具体 |
| --- | --- | --- |
| `tests/cases/token/expressions/expr-yield-await-context.ts` | `ExpressionStatement+2, YieldExpression-1, NumericLiteral-2, AwaitExpression-1` | `const o = { *m() { yield 3; }, async n() { await 3; } }` 里那一格的 yield/await |
| `tests/cases/token/statements/st-comment-holds-brace.ts` | `ReturnStatement-1, NumericLiteral-1` | `const arrow = () => /* { */ { return 3; }` 的 return |

**所以这不是「还有别的开关泄漏」**：恰恰相反，这两个文件过去能过，是因为旧 fallback 的泄漏把增量初始化器
目录留在了原地；真 legacy 建树本来就在这两格是错的。只压 `EnableIncrementalVariableShapes` 的配置里
这两条一模一样（§2.1），也证明与「多压了 `EnableIncrementalShapes`」无关。
要清零它们得修 legacy 初始化器的原子建树（A4b / A4c 那一族），不是本 WP 的 ownership。

验收口径对照：**`ok→crash` 0 条** ✓；**`ok→diff` 2 条** ✗（上面两条，已给文件 + 首错 + 最小复现 + 归因）。
