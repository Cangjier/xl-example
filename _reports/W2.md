## 1. 结论先行：任务书的归属假设被最小复现否证

任务书说「首因在 `statement-possible-shape` 的壳族选择，不是收口」。**这条不成立**。两行复现：

```ts
function f() { }
const w = 1;
```
```
TS   (2): FunctionDeclaration[0,16) / FirstStatement[16,29) "const w = 1;"
OURS (2): FunctionDeclarationShape[0,16) / ExpressionStatementShape[23,29)   ← `const` 整个不见了
```

`tmp/trace.mjs` 把每一格的候选判定打出来，实测：

```
SourceFile char 22 " "          ← 到第 22 字符 SourceFileShape 才重新拿到控制权
SourceFile char 23 "w"
  VariableStatementPossibleShape.Compute@2  Common[23,24) "w" -> 0     ← units[2] 是 `w`，不是 `const`
  ControlFlowStatementPossibleShape.Compute@2 -> 0
  RootExpressionStatementPossibleShape.Compute@2 -> 1                  ← 表达式壳 Accept
```

**`VariableStatementPossibleShape` 从来没在 `const` 那一格被问过** —— 因为 `const` 这五个字符压根没进根层
`Data`。它不是「让位」，是**根本没有参赛**。所谓「壳挂错类型」是下游症状，不是首因。

## 2. 首因：`FinishShell` 换掉壳之后，死壳还挂着它的 `MountedUnit`

`tmp/trace2.mjs`（逐字符记录「谁在处理」）：

```
> SourceFileShape @9
  > FunctionDeclarationShape[0,-1) @9       ← `function` 关键字格 MountShell
    > Bracket[10,-1) @11
    < Bracket[10,12) end=12
    > BlockShape[13,-1) @14                 ← 函数体 `{ }`
      > Bracket[13,-1) @14
      < Bracket[13,16) end=16               ← `}` 在 16 收口
    < BlockShape[13,16) end=22              ← ★ 块体一直吃到第 22 字符
  < FunctionDeclarationShape[0,-1) end=22
< SourceFileShape[0,-1) end=22
```

块体在 16 就已经 `Closed`，却继续跑到 22 —— 正好吞掉 `\nconst`（16..21 六个字符）。
`tmp/trace3.mjs` 证实那六格里 `BlockShape.ExitOrPre` 返回 `Nothing`、`Default` 是空实现，
**字符被消费掉但不产生任何单元**。

链条是这样的（`UnitToken.Process` 的循环顶）：

```ts
const parent = this.Parent;
if (parent !== null && parent.MountedUnit !== this) return;   // 唯一的「交还」判据
```

- `}` 那一格：`Bracket.Close` → `BlockShape.ComputePossibleShapes` → 转问父单元 →
  `FunctionDeclarationEndPossibleShape.ComputeByIndex` 在 `BlockShape` 格 **Accept**（`tmp/trace4.mjs` 实测
  `@5 BlockShape[13,16) -> 1`），`FinishShell` 把壳换成 `FunctionDeclarationShape`。
- `FinishShell` 清了 `parent.MountedUnit === shell`，**但没有清 `shell.MountedUnit`**。
- 于是死壳（已被换掉、已经不在 `Data` 里）仍然 `MountedUnit === block`；
  块的循环每格都过判据「我还是我父单元的 `MountedUnit`」，继续跑，把下一行字符吃掉。

**与 D2b §3 的 `[D2b:UNMOUNT]` 是同一只手**（「收口发生在逐字符循环里，每层只问『我还是不是我父单元的
`MountedUnit`』」），只是那一次在 `variable-declaration-list` 的 list 指针上，这一次在**壳→体块**这只指针上。

## 3. 改动：`[W2:UNMOUNT]`（`typescript/tokens/declarations/body-guide-util.xl.md`，+14）

```ts
const at = parent.Data.indexOf(shell);
if (at >= 0) {
  parent.Data.splice(at, 1, built);
  shell.MountedUnit = null;      // ← 新增：壳已被换掉 ⇒ 死壳，不再持有子单元
}
built.Parent = parent;
if (parent.MountedUnit === shell) {
  parent.MountedUnit = null;
}
```

- **只清「真的被换掉」的那一只**：`at >= 0` 才清。`at < 0` 说明壳不是这里的直接子单元、它可能还活着，
  一个字节都不动。
- **不碰深层链**：块自己的 `MountedUnit`（体括号）此刻已 `Quit`，清它没有意义也没有必要。
- **唯一调用点族**：`FinishShell` 只被 4 个 `*-declaration-end-possible-shape`（class / enum / function /
  module）调用，全部只在**增量壳**路径上；而壳只在 `EnableIncrementalShapes = true` 时才挂。
  ⇒ 默认关时这段代码**一行都不执行**（§5 四道门逐项与 base 相同，是这一条的实测证据）。
- **为什么放在 `body-guide-util`**：任务书写的写域是 `statement-possible-shape` + 必要接线；实测证明首因
  不在那个文件（§1），而这只悬空指针的**唯一收口点**就是 `FinishShell`。改 `statement-possible-shape`
  一个字节也修不掉这 4 条。**这是本 WP 与任务书唯一的偏离，原因在上述复现里。**

## 6. 唯一的 churn：`stmt-r1242` DIFF→CRASH，是**既存**隐性崩溃被显式化

两跳实测（`tmp/twohop.mjs`，`EnableFileFallback = false`）：

```
shell=true  -> FAIL CatalogGuide: 没有候选形状可以构成（宿主 ConditionalExpressionShape，下标 5）
shell=false -> FAIL CatalogGuide: 终结候选与其它候选同时成立（宿主 SourceFileShape，下标 199）
```

- **第二跳本来就是坏的**（D5 §1 的 15 条同一条 legacy 根层歧义，索引 199）。base 上它**不可见**，因为
  第一跳「成功」了 —— 靠的正是这个 bug：`function h(p: 'x') { }` 把下一行 `const` 吃掉，`const r = a ? b : 'x';`
  于是被当成 `r = a ? b : 'x'` 的表达式语句，DIFF 收场，永远走不到第二跳。
- 本 WP 不再吞字符 ⇒ 这条语句真的走增量变量初始化器 ⇒ 撞上一个**独立既存缺口**：
  `const r = a ? b : 'x';` 单独一条就失败（base 同然，实测）：

  ```
  shell=true  -> FAIL …（宿主 ConditionalExpressionShape，下标 5）
  shell=false -> OK          ← base 上靠文件级 fallback 救回，所以从没被看见
  ```

  最小化到一行：`const r = a ? b : 1;` PASS、`const r = a ? b : c;` PASS、`` const r = a ? b : `x`; `` PASS，
  **只有「右段操作数是字符串字面量」失败**。根因在 `ConditionalMemberPossibleShape.ComputeByIndex`：

  ```ts
  if (before instanceof ColonTokenShape) {
    return unit instanceof Common ? ShapeStates.Accept : ShapeStates.Reject;   // `'x'` 是 ConstString，不是 Common
  }
  ```

  修它要连 `BuildOperand`（只吃 `Common` → `IdentifierShape.FromBasicToken`）一起扩，是**增量变量初始化器
  目录（A4b/A4c）**的一条真缺口，不是一行补丁，也不在本 WP 写域。

**为什么照旧交**：C10「宁可显式失败」——base 那份 DIFF 本身就是错的树；本 WP 让它变成显式崩溃，并把
第二跳的坏账暴露出来。判定上 `added=0`（没有任何文件从 PASS 变成失败），`DIFF→CRASH` 记在 `changed`。
**给 Lead 的处置选项**：若合并口径要求 `crash` 严格 20、且不接受任何 `changed` 里的变差，本 WP 的改动是
**单 hunk、可整段 revert**；但那样会退回 diff 88 / crash 20 / fallback 143，且这 4 条里 3 条重新 DIFF。
另一个更划算的处置是把它挂给 A4b/A4c：那条缺口一修，`stmt-r1242` 第一跳即通过 ⇒ 差异 **78**、churn 归零。
