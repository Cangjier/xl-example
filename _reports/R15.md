## 0. 一句话结论

**任务书对 #16 的描述（「`in` 被 for-in 头吞」）与实测不符**：`in` 只是第一个被抓到的实例，
真正的判据缺口是「**无类型注解的声明、初始化器根已经是一条建好的表达式形状**」时，
`Common` 格上的 ASI 收口判据 `CanEndStatement → EndsAtLineBreak → EndsExpression` 只认**单元**，
对 `BinaryExpression` / `ConditionalExpression` 这类**已建形状**恒答 `false` ⇒ 声明在下一格收不了口，
把下一条语句整条吞进 `Data`（终态里下一条语句的 `VariableStatement`/`List`/`Declaration`/操作数全丢）。

同一条判据让 `const h = x instanceof Y` ⏎ `const i = "k" in obj` 里的 `i` 那一行整段消失，
`InKeyword`/`StringLiteral`/`BinaryExpression` 一起消失——所以「`in` 吞并」只是这条判据的**症状**，
单独给 `in` 写特判完全修不到别的运算符（`+` `===` `&&` 三元 `instanceof` 同一个坑）。

#18 的首跳也不在 `TaggedTemplateExpression` 的 build 本身，而在**两处**：
`TaggedTemplatePrimaryPossibleShape.IsBuildable` 只放行「模板之后只剩收口」（不认「后面还有一条模板」，
而那条模板的**标签**正是本模板），以及收口格 `FinishIncremental` 在「根不是括号容器」时**静默丢弃**
根之后的所有代码单元（`.b` 那一族）。

## 1. #16 的首跳（`ex-unary-ops`，R8 记「被 for-in 头吞、无残留」）

`tshape-judge steps`（`tmp/steps-*`）与 `tmp/r15-last.mjs` 的逐格末条语句实测：

```
step 181 "Y"   VariableStatement[157) … BinaryExpression[168,-1)  ← x instanceof Y
step 182 "\n"  VariableStatement[157) … BinaryExpression[168,182)  Identifier(Y)
               WrapSymbol "\n"                                     ← 换行进了**声明**，但声明不收口
step 183 "c"   … Common "c"      ← 下一条语句的 const 被吞进 h 的 VariableDeclaration
step 198 "n"   … Common "in"     ← 整行 `const i = "k" in obj` 都在 h 的声明里
step 211 " "   VariableStatement[182) … VariableDeclaration[210) Identifier(j)   ← i 整条被清掉
```

修前 `tshape-judge ts`：`VariableStatement-1 VariableDeclarationList-1 VariableDeclaration-1 Identifier-2
BinaryExpression-1 StringLiteral-1 InKeyword-1`（R8 的读数）。

**判据在哪一格丢**：`VariableDeclarationEndPossibleShape.ComputeByIndex` 的 `Common` 分支 →
`DeclarationAsiBoundary.CanClose` → `StatementBoundaryUtil.CanEndStatement` → `IsAsiBoundary` →
`EndsAtLineBreak` → `StatementScanner.EndsExpression(previous)`。`EndsExpression` 读的是
`Common`/`Symbol`/`Bracket`/`String` 这几种**单元**；`previous` 是已建形状时恒 `false`。
`CanEndDeclarationTail` 同理（末尾不是 `Symbol(">")` 时统一转发 `CanEndExpressionAt`）。

**为什么以前没暴**：`const a = o.k + 1` ⏎ `const b = 2` 这类「初始化器还是纯 raw」的格子
`EndsExpression(Common "1")` 为真，收口正常；只有候选**提前把运算物化成形状**的形态
（`1 + 2` / `x instanceof Y` / `in` / 三元 / `f() + 1`）才会走到这根空档。

## 2. #18 的首跳（`expr-tagged-template-nested-tag`）

修前 3 条（`a1` / `a2` / `a7`）的声明只到标签为止，模板整段消失：

```
CJ  VariableDeclaration [538,544) "a1 = a"        ← 只有标签
    Identifier [543,544) "a"
TS  VariableDeclaration [537,552) " a1 = a`x``x`.b"
    PropertyAccessExpression → TaggedTemplateExpression → TaggedTemplateExpression
```

两种形态实测：

| 片段 | 修前 |
|---|---|
| `` const x = a`t` `` | ok |
| `` const x = a`t``u` `` | **丢 2 个模板** |
| `` const x = a`t`.b `` | **丢 TaggedTemplate + 模板 + `.b`** |
| `` const x = a`t``u`.b `` | **丢 2 个模板 + `.b`** |
| `` const x = a`t`(1) `` / `` a`t`[0] `` / `` a`t`! `` / `` a`t` + 1 `` | ok（括号/后缀有容器或运算符面接手） |

**两处 build/close 缺口**：

1. `TaggedTemplatePrimaryPossibleShape.IsBuildable` 的第三道闸门是
   `PrimaryAtomGuard.IsTerminalAfter(unit, context, **false**)`——`allowTemplate` 档位存在
   （标识符候选开它就是为了 `` a`x` `` 里的 `a`），但模板候选自己没开。于是「模板之后还是反引号」
   （`` a`t``u` ``，本模板是下一条模板的**标签**）被判成「不是收口格」⇒ 链根本建不出来。
   同一格里 `IsTerminalAfter` 对 `.` 也答 false，于是 `` a`t`.b `` 连一级模板都建不出来。
2. 收口格 `VariableDeclarationShape.FinishIncremental`：`builtShape !== null` 且 `raw` 里还有代码单元时，
   只对**括号容器**（`ExpressionAtomRegistry.HasContainer`）走「整条 `ExpressionBuilder` 原子重建」，
   其余形态落到 `[D3a:ORPHAN-OPERATOR]`——而那条判据只认 `OperatorTable.IsBinaryOperator`。
   `.` 不是二元运算符 ⇒ 根之外的 `模板` + `.` + `b` **静默清掉**（C10 明确禁止的错树）。

## 6. 遗留与边界

1. **`expr-generic-inst-statement`（R8 #19，structural=4）没修**：首跳不在本趟两条判据上——
   `declare function f<T>(): T` ⏎ `f<string>;` 里**声明壳自己不收口**（`DeclarationShellEndCode` /
   `CanEndDeclarationTail` 这一族，等价于「`declare function` 之后换行 + 一条以标识符起头的表达式语句」），
   `f<string>;` 整条被吞进 `FunctionDeclaration` 的 `Data` 再清掉。
   最小复现：`declare function f<T>(): T` ⏎ `f<string>;`（`tmp/r15-last.mjs` 实测 step 279 起把
   `f < string > ;` 全部收进 `FunctionDeclaration`）。它与 #16 是**两条不同判据**，本趟没动。
2. `ex-await-yield`（12）与 `stmt-r1236-value-word-brace`（6）未动，与基线逐字相同。
3. `?.` 成员访问（`` a`t`?.b ``）仍不在 `MemberFollows` 的字符集里（只认 `.`）：判据刻意保守，
   等 `?.` 的续接面进目录再放行。
4. `[D3a:ORPHAN-OPERATOR]` 改成「任何越出根区间的代码单元」后，该族从**静默错树**变成**显式失败
   → 文件级 fallback**（C10）。默认档 fallback 因此 +1；legacy 档不受影响（开关关闭时一次都不经过）。
