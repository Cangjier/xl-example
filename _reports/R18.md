## 1. 首跳（实测，不是推断）

探针：临时在 `build/ts` 的三处入口打点（`DeclarationAsiBoundary.CanCloseAtLineBreak`、
`VariableDeclaration{List,}EndPossibleShape.ComputeByIndex`），用
`function* gen() {` ⏎ `  const c = yield` ⏎ `  const d = yield 1` ⏎ `}`（`tmp/m18/c2.ts`）跑逐字符驱动：

```
[CLaLB]enter ti=4/5  cur=Common trivia=false txt="yield"     ← 声明 Data=[c,␠,=,␠,yield]，本格就是"最后一个代码单元"
（无 ti=5：trivia 下标一次都没被问过）
[CLaLB]enter ti=6/7  cur=Common trivia=false txt="const"     ← 下一行首个代码单元
[DECLEND]/[LISTEND] 同样只在 ti=4 / 6 上被问
```

- **trivia 格恒假这件事是真的，但不是成因**：`VariableDeclarationEndPossibleShape` 的 trivia 分支与
  `VariableDeclarationListEndPossibleShape` 的 `super` 转发都拿**trivia 自己的下标**去问
  `CanCloseAtLineBreak`，而该判据第一句就是 `current.IsTriviaToken ⇒ false` ⇒ 这两处调用永远答 `false`
  （R12 试的「在 trivia 分支补一句」正是死在这里）。但驱动层根本不会在 trivia 下标上问候选，
  所以即使把它改对也不会触发收口。
- **真正的首跳在 ti=4 那一格**：`CanCloseAtLineBreak` 的其余条件全部成立
  （`LastCodeIndex === tokenIndex` ✓、`HasClosableShape` ✓、`StartsNewStatementLine("yield") = true` ✓，
  下一行的 `const` 跨行可见），只死在 `StatementBoundaryUtil.CanEndDeclarationTail(units, 4)`：
  它走 `ExpressionStatementPossibleShape.CanEndExpressionAt`，`CanEndExpression` 先把 `yield` 当语句词
  排除 ⇒ `false`；`shapeTail` 分支要求 `HasAnnotationShape`（本条声明没有 `:`）⇒ 也 `false`；
  `IsBlockHostBoundary` 要求下一个显著字符是宿主 `}`（这里是 `c` of `const`）⇒ 三路皆否 ⇒ 收口不发生。
- 同理 `CanClose`（ti=6 的 `const`）走的是同一份尾判据，也答 `false`。两格都不收口 ⇒
  `const d = yield 1` / `const e = yield* other()` 全进第一条声明的 `Data`，到块体 `}` 收口时
  `FinishIncremental` 的 `builtShape === null` 分支用 legacy `ExpressionBuilder` 从 `yield` 之后读不完
  ⇒ `incremental-error @ line 9 「declaration 初始化器未读完」`（与 R12 §6 逐字同一条）。

### 1.1 为什么裸 `yield` 一定是完整表达式（TS 地面真值）

`ts.createSourceFile` 实测四格，都证明 `yield` 的操作数**不跨行**：

| 源码 | TS 结果 |
|---|---|
| `function* g(){ const c = yield` ⏎ `foo }` | `YieldExpression@26-32`（止于 `yield`）+ `ExpressionStatement(foo)` |
| `function* g(){ const c = yield` ⏎ `1 }` | `YieldExpression@26-32` + `ExpressionStatement(1)` |
| `function* g(){ const c = yield` ⏎ `const d = 2 }` | `YieldExpression` 无操作数 + 第二条 `VariableStatement` |
| `const c = yield` ⏎ `const d = 2`（顶层） | `Identifier(yield)`，声明止于 `yield` |

即：生成器里是「无操作数的 `YieldExpression`」，非生成器里是普通标识符——**两种读法都是完整表达式**。
所以这一格不需要「当前函数是不是生成器」的上下文，也不新写第二套上下文判据。

### 2.1 第二处为什么必须修（wide-ast 才看得见）

`tshape-judge ts` 的驱动是**一次一字符**（`new SourceRange(doc, i, i+1)`），`SourceFileRunner.Parse`
/ wide-ast 的驱动是**窗口 128**（`SyntaxContext.Process`）。同一份源码、同一套开关，
`const d = await g()` ⏎ `const e = 2`（块体内）在两种驱动下结果不同：

```
window=1  : 正确（两条 VariableStatement）
window=4  : 错（list 的 Data 里塞满原始单元）
window=128: 错（同 window=4，且不抛异常 ⇒ 不走 fallback ⇒ 静默错树）
window=32/64: 抛错（`括号内没有表达式` / `语句没有读完`）
```

机制：收口发生在**窗口中间**。`BlockShape` → `statement` → `list` → `declaration` 四层
`UnitToken.Process` 的 while 循环此刻都还挂着，每层的退出守卫只问「我还是不是我父单元的
`MountedUnit`」。只清宿主指针（`host.MountedUnit = null`）时，`statement` 的循环确实会退出，
**但 list 的循环先进**——它问的是 `statement.MountedUnit === list`，这个指针没清 ⇒ 它把下一行的字符
继续 `Add` 进**已经关闭**的列表。root 宿主上 D2b 早就补了这一句，块体宿主上留着，单字符驱动因为
「一次只喂一个字符、收口正好落在窗口最后一格」而永远看不到。

修后 `wide-ast` 默认档 **3 → 2**，`ex-await-yield` 整条消失；`FileFallbackCount` 75 一位没动
（不是「靠 fallback 兜住的那批文件变差了」，是它们本来就没走到这一格：`samples/declarations.ts` 仍是 1）。
