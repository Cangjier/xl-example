## 3. source 透传路径

```
调用方（T2：Bracket.OnBracketCreatedEvent / 各 basic token 的 Close）
  → IComputePossibleShapes.ComputePossibleShapes[ByIndex](..., source?)     ← 可选，缺省 Close
    → UnitToken 的实现（T1 未改：仍转调 CatalogGuide 且不传 source → Close）
      → CatalogGuide.ComputePossibleShapes(host, context, source?)          ← 透传给 ByIndex
        → CatalogGuide.ComputePossibleShapesByIndex(...)                    ← 进入候选判定前写 cache
          → PossibleShapeCache.Source = source ?? PossibleSource.Close      ← 唯一载体
            → 候选的 PossibleShape.ComputeByIndex(units, tokenIndex, cache)  ← 签名不变，读 cache.Source
```

要点：

- **入口写入点只有一处**：`CatalogGuide.ComputePossibleShapesByIndex`，位于 `token === undefined` 早退之后、候选循环之前。越界调用不会改动缓存。
- **`UnitToken` 仍是「不传 = Close」**：这正是 T1「调用点不需要显式传参」的实现方式；T2 再统一显式化并让它透传。
- `EndPossible.BuildByIndex` 与普通候选走同一份 cache，因此终结候选也能读到 `Source`。

## 4. cache 语义（不按 source 分槽）

- `Source` 是**标量字段**，不是槽位内容；`Values` / `Share` 的数组布局、槽号发号方式都没变。
- 生命周期：`CatalogGuide.ComputePossibleShapesByIndex` 写入 → 本次判定可读 → `BuildByIndex` 后的 `Reset()` → `Clear()` 复位为 `Close`。所以**下一次判定读不到上一次的来源**。
- `Share` 不受 `Reset` 影响，T1 **没有**给它加 source 维度的失效判据（按任务要求「后续纳入」，先不做行为）。见 §6。

## 6. 未决风险

1. **`Share` 的 source 失效判据仍未做**（按任务约定）。双触发源下「同一格判两次」会成为常态，`Share` 不清而只靠 `Start`/长度判新鲜度的共享数据可能拿上一来源的结论判下一来源。T3/T5 里凡读 `Share` 的候选都要注意。
2. **双触发重复 build 未缓解**（T6 §4.1）：`Reset()` 让第二次触发等价于重开一局。T1 只提供来源，没有「这一格是否已建过」的判据——那是 T2 的前置。
3. **顺序陷阱未动**（T6 §4.3）：`Bracket.OnBracketCreatedEvent` 触发时新括号自己的 `CatalogGuide` 还是 `null`，只能问父层目录。T2 需要决定把 BracketCreate 触发点挪到 `BracketRoleHook` / `Install` 之后。
4. **`UnitToken` 尚未透传**：T1 下即使调用方传了 `BracketCreate`，经 `UnitToken` 到 `CatalogGuide` 也会退化成 `Close`。这是有意的（零行为），但 T2 必须补上，否则 BracketCreate 永远到不了候选。
5. **「3 签名」口径**：`IComputePossibleShapes` 实际只改了 2 个方法，`OnBracketCreatedEvent` 未加 `source`。若 T2 需要「括号创建事件也带来源」，那是 T2 的接口扩展，不要回头改 T1 的默认语义。
6. `Source` 在 `Clear()` 里复位意味着**判定结束即回到 Close**；任何想在 `Build` 之后异步/延迟读来源的候选会读到 `Close`。当前没有这种用法，但这是该字段的明确生命周期边界。
