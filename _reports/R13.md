## 0. 一句话结论

**首跳不在 `mapped-type-shape`，也不在 `type-builder` 的泛型实参解析，更不是 `>` 没被消费。**
泛型实参槽里的映射类型**本来就能建**（同一个写法带 `;` 是 `ok`，`type X = Promise<{ … }>` 也是 `ok`）。
失败发生在 **EOF 收口这一格的 `ambient` 判定**：

`FunctionDeclarationEndPossibleShape.BuildByIndex` 用「回到整个 `shell.Data` 找任意已闭合 `{`」
来回答「这条声明有没有函数体」。`Promise<{ -readonly [P in keyof T]: T[P] }>` 停在文件末尾时，
泛型实参槽里的**映射类型括号被当成函数体** ⇒ `ambient=false` ⇒ `FromUnits` 在末单元是 `>`
（既不是体、也不是 `;`）时抛「函数声明缺少函数体或分号」⇒ R9 的 `TryToClose` 兜不住、
整条声明留在 raw 记号上（20 个 basic token、`moved` +1 字节都是这一处的下游）。

修法只有一处：`hasBody` 改问**末代码单元**，且闭合 `{` 只在 `TypeBuilder.IsBodyBrace` 认它是体时才算体
——**与 `FromUnits` 建树时是同一份判据**。不是为映射类型写的特判。

### 1.1 首跳的直接证据（在 built JS 里临时给 R9 的 `catch` 加一行 `console.error`，量完即撤）

```

  at FunctionDeclarationEndPossibleShape.BuildByIndex (…/function-declaration-end-possible-shape.js:131)
```

- 与 R9 §7 的「`FromUnits` 在这一形态上仍会抛错，`try/catch` 退回修复前行为」逐字吻合；
- 但**抛错原因不是映射类型解析失败**：`ParseMappedType` 根本还没被调用（`FromUnits` 在

  `Common/Symbol/Bracket`，`Promise`、`<`、`{ … }`、`>` 一个都没建 —— 下游症状，不是首跳。

## 2. 根因

```ts
// 修复前（BuildByIndex）
let hasBody = false;
for (let at = 0; at <= lastCode; at++) {
  const candidate = shell.Data[at];
  if (candidate instanceof BlockShape) { hasBody = true; break; }
  if (candidate instanceof Bracket && candidate.StartBracketChar === "{" && candidate.Closed) { hasBody = true; break; }
}
FromUnits(shell, 0, lastCode, context, !hasBody, false, shell.Pos);   // ambient = !hasBody
```

`shell.Data` 在收口时是整条声明的 raw 单元，**`{` 出现在任何位置都会被扫成体**：

- `declare function f(): Promise<{ -readonly [P in keyof T]: T[P] }>`（无 `;`，EOF）：
  末代码单元 `>` ⇒ `FromUnits` 的 `lastIsBrace=false`、`lastIsSemicolon=false`、
  `ambient=false` ⇒ 抛「函数声明缺少函数体或分号」；
- 同一路径上 `declare function f(): { a: number }`（无 `;`，EOF）为什么没坏：
  末单元本身就是那个 `{`，`lastIsBrace=true`，`FromUnits` 走不到抛错分支（`ambient` 的错值被巧合绕过）；
- `Box<{ … }>;` / `Promise<{ … }>;` 为什么没坏：末单元是 `;`，`ambient` 同样不被读。

即：**`hasBody` 的语义错位**——它要回答的是「这条声明是否**以**函数体收尾」，
却实现成了「沿途**出现过** `{`」。而 `FromUnits` 建树时用的是窄得多的判据
（`lastIsBrace && TypeBuilder.IsBodyBrace(code, last)`）。两处判据不一致，就是这一格。

## 3. 改动（1 个源页，1 个表达式）

`typescript/tokens/declarations/function-declaration-end-possible-shape.xl.md` · `BuildByIndex`：

```ts
const tailUnit = shell.Data[lastCode];
const hasBody = tailUnit instanceof BlockShape
  || (tailUnit instanceof Bracket && (tailUnit as Bracket).StartBracketChar === "{" && (tailUnit as Bracket).Closed
    && TypeBuilder.IsBodyBrace(shell.Data, lastCode));
```

- 只有**末代码单元**可能是函数体，所以不再回扫整个 `Data`；
- 闭合 `{` 是否为体，直接复用 `TypeBuilder.IsBodyBrace`（`FromUnits` 内部判断体括号的同一个函数，
  `type-builder.xl.md:476`）：`function f() {}` 的 `{` 前是 `)` ⇒ 是体；返回类型 / 泛型实参里的 `{`
  前是 `:` / `<` / `,` ⇒ 不是体；
- `BlockShape`（已在 `{` 那格被 `OpenFunctionBody` 包好的体壳）仍算体，原有的真函数体形态不变；
- 方法说明里补一条 bullet，指明 `ambient` 的口径与 `[R13:MAPPED-IN-GENERIC]` 标记；
- **没有改** `mapped-type-shape.xl.md`（它只是 `ReadonlyToken/TypeParameter/QuestionToken/NameType/Type`
  的字段容器，建树在 `type-builder.ParseMappedType`，本轮证明它并不参与这次失败）、
  **没有改** `ParseMappedType` / `ParseTypeLiteral` / `FromUnits`、**没有改** R9 的 `TryToClose`、
  **没有改** basic token。

## 6. 与任务书假设的偏差（如实记）

任务书第 3 条要求「修在 `mapped-type-shape` / `type-builder` 的泛型实参 / EOF 收口」。
实测首跳在**上游一格**：`FunctionDeclarationEndPossibleShape.BuildByIndex` 的 `ambient` 判定，
它属于「EOF 收口」这一段，但不在这两个页里。理由：

1. 泛型实参槽的解析没有缺口——`TypeBuilder.ParseType` 对 `Promise<{ … }>` 在带 `;` 的收口里
   一次就建对了（矩阵 #1/#3/#5 修复前即 `ok`），所以改 `mapped-type-shape` / `type-builder`
   没有可改的判据（`MappedTypeShape` 只有字段与构造函数，`ParseMappedType` 在失败路径里根本没被调用）；
2. R9 已明确不要在 `TryToClose` 里加特判，本轮遵守；改的是同一个候选自己的 `BuildByIndex`，
   交给 `TryToClose` 的仍是原来那一调 `EndPossible.BuildByIndex`，R9 的代码一行未动；
3. 判据复用 `TypeBuilder.IsBodyBrace`，等于把「体括号」的认定收敛到 `type-builder` 已有的那**一份**，
   不再让收口侧和建树侧各有一套。
