## 0. 一句话结论

**首跳既不是 `DeclarationShellEndCode`，也不是「只看同一行」**：`declare function` 的壳不是
`StatementEndPossibleShape` 那一族——它由 `FunctionDeclarationPossibleShape` 提前挂出，
终结候选是 `FunctionDeclarationEndPossibleShape`。那条候选的 `[W5:FUNCTION-ASI]` 分支
**只认声明 / 语句关键字的闭集**（`StatementHeadWords`），`f` 不是关键字 ⇒ 判不出边界
⇒ 壳一路吃到 EOF，`f<string>;` 整条被 `BuildByIndex` 的无体（`ambient`）分支丢掉。
修法：把这条 ASI 判据的第二层换成**同一份通用判据** `DeclarationAsiBoundary.StartsNewStatementLine`
（跨行 + 下一行起一个不续接的单词），再叠一张**声明头续接词**否决表。

口径先钉死：`EnableIncrementalShapes` 的**默认值就是 `true`**（`statement-route-util.xl.md:109`），
所以「默认 true 档」= 本判据生效、壳提前挂出的那一档 = `tshape-judge` / `wide-ast` / `tts` 的读数；
开关压回 `false` 的 `--legacy` 档走 `FunctionDeclarationPossibleShape` 的原子建树（`FromUnits` /
`SplitAt`），**修前就已经是对的**，本趟一个字节不动。

## 1. 首跳（实测，`tmp/r16-probe*.mjs`）

`declare function f<T>(): T` ⏎ `f<string>;`，默认 true 档逐格实测：

```
[FDEND tok=f -> 0] … [FDEND tok=string -> 0] … [FDEND tok=; -> 0]     ← 终结候选一格都不 Accept
[FromUnits start=0 tok=17 ambient=true] data=declare| |function| |f|<|T|>|(|:| |T|\n|f|<|string|>|;
    at FunctionDeclarationEndPossibleShape.BuildByIndex
    at FunctionDeclarationShape.TryToClose
    at SourceFileShape.Process
```

`tokenIndex=17` 是 `f<string>;` 的 `;`：壳把自己的 `Data` 整段交给 `FromUnits`，`FromUnits`
只建到返回类型 `T`（`src=[0,26)`），剩下的 `f < string > ;` **不出现在任何节点里**
⇒ 终态少 `ExpressionStatement` / `ExpressionWithTypeArguments` / `Identifier` / `StringKeyword`
（`tshape-judge ts` 的 `structural` 正是这 4 条）。

判据链（`FunctionDeclarationEndPossibleShape.ComputeByIndex` 第 3 条分支）：本格不是闭合
`BlockShape`、不是闭合 `;` ⇒ 取「不含本格」的上一格 `previous`（= 返回类型的 `T`），要求
`!IsOpenTail(previous) && StartsNewDeclarationLine(previous)`。`IsOpenTail(T)` 答 false（正确），
`StartsNewDeclarationLine(T)` 读下一行首词 `f`，旧实现只有
`StatementHeadWords.includes(word)` ⇒ false。

所以不是「声明壳只看同一行」：**这条 ASI 判据的词表只认关键字**，下一行只要是标识符起头的
表达式语句就看不见。`DeclarationShellEndCode` 那一族（`StatementBoundaryUtil.IsDeclarationFollowBoundary`
判据三：`CanEndDeclarationTail` + 单词起点）本来就答 true，但它不是 `declare function` 的收口人
（`docs/statement-ast-pipeline.md` 路由 8 的直建族 ⇒ `FunctionDeclarationEndPossibleShape`）。

**为什么不是 `declare function` 特判**：判据只看「上一格不是开口尾巴 + 下一行起一条不续接的语句」，
与声明里有没有 `declare`、有没有 `<T>`、有没有返回类型全无关——`function f(): T` ⏎ `f()` 同一条
（矩阵 #5/#9/#11）。`declare var/const` 走 `DeclarationAsiBoundary`，本来就在通用判据上
（矩阵 #13–#15 修前修后都 ok，作为对照）。

**为什么否决表不能省**：函数声明的头部**可以跨行继续**，那些格子下一行起的是 `extends` / `is`
这样的续接词，收口就是错树（`gap-sweep-newline-generic-03` / `gap-r931-asserts-is-newline` 一族）。
`StatementTokenSets.IsExpressionContinuation` 的闭集只有 `in` / `instanceof` / `as` / `satisfies`
（表达式续接），不含 `extends` / `is`，所以声明头的这一档单独登记一张表并在报告里点名；
矩阵 #17 / #18 是它的守卫。

**开关门控原样保留**：`if (!IsIncrementalShapesEnabled()) return false` 不动——这条判据服务的是
「壳提前挂出、后续 raw 单元进壳」那条路（`FunctionDeclarationPossibleShape` 的 `MountShell` 分支
本身就只在增量档里），`--legacy` 的原子建树不经过本候选。本趟只动词表，不动门。

## 5. 边界与遗留

1. **`HeadContinuationWords` 是「声明头续接词」闭集**，与 `DeclarationAsiBoundary.ContinuationWords`
   （表达式续接：`in` / `instanceof` / `as` / `satisfies`）是两张表、两个问题。将来若出现第三种
   「跨行的下一行首词是不是续接」的字符级消费者，应把两张表并进 `StatementTokenSets` 做单一来源
   （现在只有两个消费者，先各留一份并登记在这里）。
2. **默认 true 档 3 → 2** 只动了 `expr-generic-inst-statement`：`ex-await-yield`(12) 与
   `stmt-r1236-value-word-brace`(6) 与基线逐字相同，未动（它们是另外两条判据）。
3. **默认 true 档 #12（`…(): T` ⏎ `f` 裸标识符到 EOF）仍 DIFF**：与本趟判据无关（没有下一行可读，
   收口落在 EOF 那一拍），修前修后同一条。
4. 未动 R9 `function-declaration-shape.TryToClose` / `FromUnits`：本趟的收口点在**终结候选**
   （`BuildByIndex` 的 `boundary` / `leftover` 机制本来就对「边界单元不是 `;` / 体括号 / EOF」的形态
   生效），`TryToClose` 只是调用方，一个字没改。
