## 1. 首跳：不是 `!` / `[]` 的 end，是「左操作数是**已建形状**时整个 `as` 没人接」

`node tmp/probe-asbang.mjs tmp/matrix/a2.ts` 打出真实内层异常（`SyntaxException.InnerException`）：

```
THROW at char 55 = ";"
inner: 增量变量形状未支持：declaration 符号 !
  at VariableDeclarationListEndPossibleShape.ComputeByIndex
  at CatalogGuide.ComputePossibleShapesByIndex
  at VariableDeclarationShape.ComputePossibleShapes
```

即：`;` 那一拍终结候选扫 `Data`，看见 `!` 就走 C10 兜底 `throw`。逐个构造的最小矩阵（`tmp/probe-asbang2.mjs` + `tshape-judge ts`，全部 `const <e> = f() ...`）：

| 构造 | 基线 | 首跳 |
|---|---|---|
| `f() as T` | **diff**（`AsExpression-1` / `TypeReference-1` / `Identifier-1` 缺，声明区间短 5 = ` as T` 被静默丢掉） | `FinishIncremental` 收下唯一根 `CallExpressionShape`，`as` 不在「根之外的二元运算符」检查里 ⇒ 静默截断 |
| `f() as T!` | incremental-error @55 | `declaration 符号 !` |
| `f() as T!!` | incremental-error | 同上（第一个 `!`） |
| `f() as T! \| U` | incremental-error | 同上 |
| `f() as T \| U!` | incremental-error @56 | 同上 |
| `f() as Box<T!>` | incremental-error @61 | 同上 |
| **`f() as T[]`**（无 `!`） | incremental-error @54 | `declaration 括号` |
| **`f() as T![]`** | incremental-error @54 | `declaration 括号` |
| `f() as unknown as T` | diff（`AsExpression-2` 缺） | 同「`as T`」的静默截断 |
| `f() satisfies T!` | incremental-error | `declaration 符号 !` |
| `(f() as T)!` | ok | —（括号里走 `ExpressionBracketPossibleShape`，另一条路） |
| `g(f() as T!)` | ok | —（调用实参括号，同上） |
| `let d!: number;` | ok | —（`BuildDefinite`） |

**所以 `!` 与 `[]` 是同一个缺口的两种症状**：`as T` 本身就没被建；`!` / `[` 只是让「静默截断」变成「显式抛错」。根因两步，同一处：

`VariableDeclarationShape.ComputePossibleShapes` 的类型面（`TypeMode`）本该在 `as` 那一格接管（注释里写着「下一格起是 `as` / `satisfies` … 时 TypeMode 接管」），但它没进去：

* `TypeCatalogFactory.StartsTypedInitializer` 的**头判据**只认：容器形状 / `Common`（标识符、`async`、`function`、类型实参调用）/ 括号 / `<`，
  末尾一句明文「左操作数是**调用** / 普通算术等其它形态**不接管**」⇒ `f()` 建出的 `CallExpressionShape`
  （由表达式候选在 `)` 关闭格建，**没有**登记进 `ExpressionAtomRegistry.Containers`）落进这一句，`entered=false`，`TypeMode` 一直 false。
  探针每格都打印 `typeMode=false starts=false`，`as` 那一格也一样。
* 就算 `TypeMode` 进去，`TryBuildTypedInitializer` 的守卫 `if (非 basic && !HasContainer) return;` 也会在同一个 `CallExpressionShape` 上让路。
* 于是 `!` / `[` 那两格由 `VariableDeclarationEndPossibleShape` 回答：`IsRawInitializer` 为假（有形状了）、
  `HasContainerInitializer` 为假（不是容器）⇒ 两条 「`[D3a:RAW-INITIALIZER]` / `[D1:RAW-INITIALIZER]` 继续等」的路都进不去 ⇒ C10 `throw`。

## 2. 修法：让增量路径自己收格（不借 fallback，不改 `source-file-runner`）

两条改动都在**增量形状路径**里，都在字符流里**提前一拍**建出节点；没有动 `source-file-runner` 的 fallback 起点，也没有让「fallback 后 legacy 正确」当成功。

**(a) `types/types/catalog-factory.xl.md`**

1. `StartsTypedInitializer` 追加 `[R11:SHAPE-HEAD]`：头是 **`ShapeToken`**（形状目录已建好的表达式形状）时，与「容器作头」同一答案 —— 有 `as` / `satisfies` 就接管：
   ```ts
   if (head instanceof ShapeToken) {
     return TypeCatalogFactory.HasTypeAssert(units);
   }
   ```
   `Bracket` / `Common` / `Symbol` 都不是 `ShapeToken`，所以原有四支的判据一个字不变；无 `as` / `satisfies` 时 `HasTypeAssert` 仍返回 false，不抢 A2/A3/A4 的写域。
2. 新增 `ParseInitializerFrom(units, head, basePos, template, context)`：与 `ParseInitializer` 同一套 `ExpressionBuilder` / 同一 `Positions` 口径，
   唯一差别是起点 —— `builder.At = 1; builder.ParseExpressionFrom(head, 0)`。`ParsePrimary` 只认登记过的容器 / 原子，
   任意形状进不去，所以必须走这一支（`ParseBinaryFrom` 的 `IsTypeOperator` 分支接 `as` / `satisfies` → legacy `ParseFollowingType`；
   `TypeBuilder.ParsePostfixType` 把 `!` 折成 `JSDocNonNullableType`、空 `[]` 折成 `ArrayType`，`!!` 逐层裹）。
   **自证**：`head` 不是第一个单元、或 `At` 没走到末尾 ⇒ 返回 `null`，调用方继续等（C10 不变）。

**(b) `declarations/variable-declaration-shape.xl.md`**

`TryBuildTypedInitializer` 的守卫从「非 basic 且非容器 ⇒ 让路」放宽成「**唯一一个** `ShapeToken` 也放行」：

```ts
let builtHead:Token | null = null;
for (let at = equal + 1; at <= last; at++) {
  if (this.Data[at].IsBasicToken) { continue; }
  if (ExpressionAtomRegistry.HasContainer(this.Data[at])) { continue; }
  if (builtHead === null && this.Data[at] instanceof ShapeToken) { builtHead = this.Data[at]; continue; }
  return;                       // 第二个非 basic 单元 = 多根，逐字让路
}
let expression = TypeCatalogFactory.ParseInitializer(raw, basePos, this.Template, context);
if (expression === null && builtHead !== null) {
  expression = TypeCatalogFactory.ParseInitializerFrom(raw, builtHead, basePos, this.Template, context);
}
if (expression === null) { return; }
```

落不落地仍由既有的两道闸决定：`ParseInitializer*` 必须**整段吃完**、`CanEndInitializer(末单元)` 必须为真（后面是 `;` / 输入结束）。
两闸任一不成立就返回 `null` 继续等 —— 不产半棵树。

**收格时机（逐字）**：`f() as T!` 在 `T` 那一格 `CanEndInitializer` 说「后面还有 `!`」⇒ 等；`!` 那一格说「后面是 `;`」⇒ 落地，
`AsExpression` 区间 `SpanNode(0, !)` 覆盖到 `!` 的 `End`（与 `ts.createSourceFile` 的 `AsExpression[9,19)` 一致）。
`T! | U` 在 `!` 那格被 `|` 挡住、在 `U` 那格落地（`UnionType`）。`T[]` 在 `[` / `]` 两格都挡、`]` 之后落地（`ArrayType`）。

## 3. 反向边界（C10 一个字没松）

* `TryBuildTypedInitializer` 仍要求「**唯一的**非 basic 单元」；出现第二个形状 / 非容器单元 ⇒ 原样 `return`（多根不接管）。
* `StartsTypedInitializer` 的 `ShapeToken` 支只加在「有 `as` / `satisfies`」上；`HasTypeAssert` 的递归范围没改。
* `VariableDeclarationEndPossibleShape` **一行未改** —— `!` / `[` 那两格的 C10 `throw` 还在，只是现在 TypeMode 先进去、根本走不到它；
  `?.` / `??` / `<` 三条 `throw/composite` 的显式拒绝账本因此逐字不变（`tts` 429 PASS 里的 3 条 `expected=throw actual=throw` 仍是
  `declaration 符号 ?.` / `??` / `<`）。
* `lex-bom-midcode.ts` 等 19 条既有差异一条没动（见 §4）。
* 未触碰 `IMPORTANCE.md`、R4 的二元优先级、R7 的箭头体。
