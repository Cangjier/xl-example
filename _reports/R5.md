# R5 — 变量语句分号的归属与 end 时机

分支 `feature/r5-semicolon`，基线 `e11272f3`（R4 已合入）。目标缺陷两条（同一条根因的两半）：

1. **`;` 归属**：`const a = 1;`（无结尾换行）的语句分号在 EOF 被静默丢掉；
2. **`;` 格 end**：语句区间因此以「最后一个代码子单元」封口——`[0,11)`，而 TS 是 `[0,12)`
   （`VariableStatement` 含 `SemicolonToken [11,12)`）。

### step 11（`;`）与 step 12（EOF）原文

```text
## step 11 ";"
SourceFileShape  pos=-  src=[0,...)
└─ VariableStatementShape  pos=0  src=[0,...)
   └─ VariableDeclarationListShape  pos=0  src=[0,...)
      └─ VariableDeclarationShape  pos=5  src=[6,...)
         ├─ IdentifierShape  pos=5  src=[6,7)  text="a"
         ├─ WrapSymbol  src=[7,8)  text=" "
         ├─ Symbol  src=[8,9)  text="="
         ├─ WrapSymbol  src=[9,10)  text=" "
         ├─ NumericLiteralShape  pos=9  src=[10,11)  text="1"
         └─ Symbol  src=[11,12)  text=";"

## step 12 "EOF"
SourceFileShape  pos=-  src=[0,12)
└─ VariableStatementShape  pos=0  src=[0,12)
   ├─ VariableDeclarationListShape  pos=0  src=[0,11)
   │  └─ VariableDeclarationShape  pos=5  src=[6,11)
   │     ├─ IdentifierShape  pos=5  src=[6,7)  text="a"
   │     └─ NumericLiteralShape  pos=9  src=[10,11)  text="1"
   └─ Symbol  src=[11,12)  text=";"
```

- 语句 `src=[0,12)`，以分号的 `End` 封口；list / declaration 仍是 `[0,11)` / `[6,11)`（与 TS 同）。
- step 12 **不再新增 shape**（只有区间封口 + 一次收口），**不再裁分号**（分号挂在语句名下）。
- TS 侧（`forEachChild`，`tmp/r5-ts-ast.mjs` 导出）：`SourceFile [0,12)` → `VariableStatement [0,12)`
  → `VariableDeclarationList [0,11)` → `VariableDeclaration [5,11)`；`SemicolonToken` 是语句的 token 字段，
  不进 AST children，但**计入语句的 end**。

## 1. 根因：两层，缺一不可

### 1.1 文件末尾的 `;` 从来没有被关闭，候选目录一次也没在 `;` 格被问过

逐字 trace（step == 字符下标）里，`;` 在第 11 拍**到达并进入 `declaration.Data`**，但它的 `Close` 从未发生：
basic token 的候选判定是 `Close → 问父单元`，而触发 `Close` 的是**下一个 token 的开头**。文档末尾的 `;`
后面没有下一个 token，于是：

- `VariableDeclarationListEndPossibleShape` 的 `;` 分支（`Accept` → `CloseAtSemicolon`）**一次都没被求值**；
- 同一份文件只要在 `;` 后多一个字符就一切正常：`let x = 1;\n`、`const a = 1; `、`const a = 1;/* c */`
  全部 `ok`（基线也是）——那一格把 `;` 关掉，走的正是 `CloseAtSemicolon`。

这就是为什么缺陷只在「文件以 `;` 结尾」时出现。

### 1.2 EOF 兜底路径不认分号

走不到 1.1 的候选路径时，收口由 `SourceFileShape.Process` 的 EOF 分支直接 `mounted.TryToClose(context)` 完成，
而这条路上：

- `VariableDeclarationShape.FinishIncremental` 把 `;` 当 trivia 一样 `continue` 掉（**静默丢弃**）；
- `VariableStatementShape.TryToClose` 的裁口判据是「**收口前**的 list 终点快照」：
  `listEndBefore >= 0 && this.EndIndex === listEndBefore`。EOF 上 statement / list 都还**没签出**
  （`EndIndex` 都是 `-1`），快照于是恒等于当前终点，判据恒成立、又恒无事可做；
- 结果是语句终点由基类从「最后一个子单元」（list = 11）补出 ⇒ `[0,11)`。

所以修法必须同时解决这两件事：**`;` 不能被丢**（归属），**终点不能由「最后一个 shape 子单元」决定**（end/trim）。

## 2. 改动

### 2.1 `;` 归属：声明交还，语句收下

`typescript/tokens/declarations/variable-declaration-shape.xl.md`

- 新增 `field TrailingSemicolon:Token | null`：**待交还的语句分号**。声明不拥有 `;`（TS 的
  `VariableDeclaration` 止于初始化器，`const a = 1;` 的声明是 `[6,11)`），但也不许丢它。
- 新增 `private method TakeTrailingSemicolon`：`FinishIncremental` 的第 0 步从 `Data` 末尾（跳过 trivia）
  摘下唯一的 `;`，记进 `TrailingSemicolon`；`Data` 里因此不再有它，声明的 `TrimEndToLastCode` 照旧收到 11。
- `FinishIncremental` 里原有的两处 `;` 过滤（`=` 之前那一段、`raw` 初始化器那一段）**不再是静默丢弃**：
  命中时同样记进 `TrailingSemicolon`（只记第一个），语句终点仍拿得到分号的 `End`。

`typescript/tokens/statements/variable-statement-shape.xl.md`

- 新增 `method AdoptTrailingSemicolon`：取 `declaration.TrailingSemicolon`，`this.Add(semicolon)`
  （`Parent` 由 `Token.Add` 设成语句自己），再给分号补一次 `TryToClose`（`Symbol.Close` 的「问父单元」落在
  语句上；语句没有目录向导 ⇒ 无事发生）。
- `Data` 顺序因此是 `[声明列表, ;]`（源码顺序）。`;` 是 basic token，`cjAst` 对拍按 `IsAstShape` 过滤，
  它不会变成多出来的 AST 节点，**只贡献语句的终点**——这正是 TS 的口径（`SemicolonToken` 不进 children，
  但它属于 `VariableStatement` 的区间）。

### 2.2 `;` 格 end：语句终点 = 分号的 `End`

分号还有后续字符的形态（`let x = 1;\n` / `; ` / `;//` …）本来就由 `CloseAtSemicolon` 收口
（`statement.SourceRange.End = semicolon.EndIndex`，既有路径，本次一个字没改）。
文件以 `;` 结尾时，收口点在 EOF 那一拍，但**终点策略是同一份**：语句先收下 `;`，基类再补终点，
读到的最后一个子单元就是分号 ⇒ `[0,12)`。

**为什么不是「在 `;` 到达那一拍就收口」**：`;` 的候选判定只在 token `Close` 时触发，而文档末尾的 `;`
后面没有下一个 token 来关它（§1.1）——那一拍在词法上不可达，不是本层能决定的事。本 WP 能做到、也确实做到的是：
**收口的时机可以晚，但终点的来源不能变**——语句终点不再由「最后一个 shape 子单元」补，而是由分号自己的 `End`
封口，step 12 因此只封区间、不新增 shape。

### 2.3 EOF 收口守卫：`TrimEndToLastCode` 不再裁分号

新增 `method TrimEndToLastCodeUnlessSemicolon(listEndBefore)`，**两条判据，缺一不可**：

1. 语句的**末代码子单元是 `;`** ⇒ 只允许裁到分号的 `End`（去掉它之后的 trivia），`;` 本身保留；
2. 否则只有「语句终点仍等于**收口前**的列表终点」才裁（旧行为：多出来的只能是 trivia）。

旧实现只有第 2 条，而它在 EOF 上两边都是 `-1`，既判不出「有没有分号」、也判不出「收到哪」——这就是 §1.2。
现在第 1 条是主判据，`listEndBefore` 降为「ASI 尾随 trivia」那一条的补充，**不再是唯一判据**。

反例保护（实测）：分号已被 `CloseAtSemicolon` 消费时（`let x = 1;\n`），语句终点比列表终点大 1，
第 2 条不成立 ⇒ 不会把分号裁掉；语句 `Data` 里也没有 `;` 子单元，第 1 条不适用。
（第一版把第 2 条整个删掉，`let x = 1;\n` / `if (a) { let x = 1; }` 立刻从 ok 退化成 `0-10 vs 0-9` —— 见 §5 的回摆。）

## 4. 分隔符 owner 的同族检查（只记录，本 WP 不改）

同一类「末尾 token 没有下一个字符来关它」的形态逐个试过，**没有复现**同类 owner 缺陷：

| 语料（都以该分隔符结尾） | 读数 | 为什么不会同错 |
| --- | --- | --- |
| `f(a)` / `f(a);` / `f(a, )` | ok | `)` 是 `Bracket` 的结束括号，`Bracket.Close` 由**括号自己的字符**触发，不依赖下一个 token |
| `const a = [1, ]` / `const o = { a: 1, }` | ok | 同上（`]` / `}` 也是括号字符）；尾随 `,` 在括号体内部由括号体目录收口 |
| `const o = { a: 1 }` / `const a = [1, 2]`（无分号） | ok | 括号关完，初始化器根已落地，ASI 收口 |
| `if (a) { let x = 1 }` / `if (a) { let x = 1; }` | ok | `}` 同上；分号在 `}` 前已经被它关掉 |
| `const [a, b] = [1, 2]` | ok | 解构绑定由 `FromBracket` 一次建出，`,` 不在顶层 Data |

结论：**同类缺陷只出现在「符号型」收尾上，而符号型收尾里只有 `;` 是语句/声明的 owner**——`,` 只在声明之间
（`OpenNext`）或括号内部，`)` `]` `}` 都是括号字符、由 `Bracket.Close` 自己触发。因此 `;` 这一处是唯一的接口面，
其余三处不需要同批修改（若要统一，应当把「末尾符号的 close 触发」做成 basic token 层的通用契约，属于 core 的写域，
不在本 WP）。
