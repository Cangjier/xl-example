## 2. 根因：一个 deadlock，四种「第一跳构造」

15 条在**次跳（legacy，`ParseCore(shell=false)`）**全部撞同一句、同一个宿主、同一个 token：
`载体 = SourceFileShape`、`下标 = EOF 哨兵`、`活着的候选 = [StatementPossibleShape]`。
程序化确认（`tmp/w3dump.mjs`，逐个打印 `EndPossible` 接受时的存活候选集）：15/15 完全同形。

机理：`CatalogGuide` 只在「**恰好一个**候选活着」时建形状（`Candidates.size === 1`）。
这 15 个用例都以 `declare const …;` 开头，于是 legacy 目录里

- `DeclareVariablePossibleShape`（ambient 变量声明候选）在 `declare` 格 Accept，
- `StatementPossibleShape`（legacy 根语句候选）在 `declare` 格也不 Reject（它的内联分流只认
  `let|const|var` 开头，`declare` 不在名单里），

两个同格双活 ⇒ `Candidates.size` 恒为 2 ⇒ **一行都建不出来**，`ItemStart` 一直是 0；
到 EOF 哨兵，`SourceFileEndPossibleShape` 在 `EndOfFileTokenShape` 上**无条件 Accept**，
而 `StatementPossibleShape` 的旧守卫是 `state.Start > 0 && EOF → Reject`——`Start` 是 0，
守卫轮不到，`Status === 1` 直接 Accept ⇒ 抛「终结候选与其它候选同时成立」。
**这就是「次跳同句」：不是 15 个语法点，是 15 个用例都以 `declare const` 开头。**

§2 的四个子族只是**第一跳**失败的地方不同（`tmp/w3dump.mjs` 的 ON 列，逐条实测）：

## 3. 改动（本次提交的唯一一处）

`typescript/tokens/statements/statement-possible-shape.xl.md` · `ComputeByIndex`：

```ts
// 旧：只在「已经建出过上一条语句」时才在 EOF 让位
if (state.Start > 0 && units[tokenIndex] instanceof EndOfFileTokenShape) {
  return ShapeStates.Reject;
}
// 新：EOF 哨兵上一律让位（不看 Start、不看 Status）
if (units[tokenIndex] instanceof EndOfFileTokenShape) {
  return ShapeStates.Reject;
}
```

**为什么这是对的而不是绕开**：EOF 哨兵没有第二种结局——`SourceFileEndPossibleShape`
在 `EndOfFileTokenShape` 上无条件 Accept（文件不能再长），所以「终结候选 Accept 而本候选还活着」
在这一格是**一定**、不是偶发；抛错永远不是正确答案。未收口的尾段本来就有归属：
同一支的 EOF 兜底 `BuildTrailingDeclaration`（按换行处的声明词切段）/
`BuildStatementSegments`（逐条建）正是为它写的，C04–C06 的边界 token 也是在那里建的。

## 5. 剩余 8 条：新落点与最小复现（下一波从这里接）

C 之后这 8 条**已经不再**撞「终结候选与其它候选同时成立」，而是走到同一个新落点：
`SourceFileEndPossibleShape.BuildByIndex` 的 EOF 尾段兜底最后一步
`ExpressionStatementShape.FromUnits(host, start, at, …)`，读到越界单元：

```
TypeError: Cannot read properties of undefined (reading 'IsTriviaToken')
  at ExpressionStatementShape.FromUnits (expression-statement-shape.js:19)
  at SourceFileEndPossibleShape.BuildByIndex (source-file-end-possible-shape.js:267)
  at CatalogGuide.ComputePossibleShapesByIndex (catalog-guide.js:46)
```

最小复现（legacy 跳，`node tmp/w3min.mjs "<片段>"`，`\n` 为换行）：

| 片段 | ON | OFF |
| --- | --- | --- |
| `declare const a: any;` ⏎ `const v = { p: 1 }` `` ` `` ``t`` `` ` `` `;` | OK | **undefined.IsTriviaToken** |
| `declare const a: any;` ⏎ `function w() { }` ⏎ `/re/g;` | OK | **undefined.IsTriviaToken** |
| `declare const f: any;` ⏎ `const q = f() as T![];` | OK | OK |
| `declare const a: any;` ⏎ `if (a) { { g() } }` | OK | OK |

读法：**`declare const` 只是让 `ItemStart` 停在 0 的那把钥匙**；真正建不出来的是后面的构造。
一旦尾段里出现「值位 `{` 后面跟 tag 模板」或「`}` 换行以 `/` 开头」，EOF 兜底的
`BuildTrailingDeclaration` 切不出段、`BuildStatementSegments` 也切不出，
落到 `FromUnits` 就越界——这正是 B2/B3 两个子族的语法点本身。

### 建议的下一步（按收益排序）

1. **B4 先做**：`declare const f: any;` ⏎ `const q = f() as T![];` 在 legacy 已经能建出来，
   只剩整文件里的 `as T!` 那一格（`AsCloseRule` / `NotNullCloseRule` 的收尾），
   `expr-as-type-nonnull-tail` 与 `expr-as-then-value-operator` 是同一句判据的两个尾巴。
2. **B2/B3 修 `BuildTrailingDeclaration` 的切段**（`source-file-end-possible-shape`）或
   让它们**不经 EOF 兜底**：给 legacy 侧补一条「值位 `{ … }` 后紧跟模板 / `}` 后换行 `/`」
   的语句边界判据（与 `StatementBoundaryUtil` 现有 ASI 判据同源），让每条语句在自己的格上建完，
   `ItemStart` 不再停在 0——这一条同时消掉 §5 的 8 条。
3. **A 与 C 可以叠加但不要单独用 A**：A（在 `declare const|let|var` 上让位）把 15 条全消掉、
   差异仍是 88，但会把 `undici-types/cache.d.ts`、`index.d.ts` 变成崩溃
   （`增量变量形状未支持：declaration 声明体`）。要叠加必须先给
   `DeclareVariablePossibleShape.BuildByIndex` 一条 legacy 兜底
   （`StatementBuilder.BuildDeclareVariableStatement`，本文件开头记的就是同一形状 / 同一 `Pos`），
   否则违反「0 条原来通过现在失败」。
