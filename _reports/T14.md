## 2. 根因：`new` 后面那只 `(` 被当成**实参括号**

`NewPossibleShape` 只认两种形态（表格第一二行）：无括号 `new C` 在**被构造者格**建、`new C(…)`
在 `)` 关闭格建。它的括号分支判据是 `Bracket + IsNewItem`——**只看「这一格是已闭合的 `(` 且条目以
`new` 开头」**，分不清这只括号是

- **实参括号**（`new C(…)`：前一个代码单元是被构造者 `C`，或后缀链尾），还是
- **括号组被构造者**（`new (E)`：前一个代码单元是 **`new` 关键字本身**）。

于是 `new (A)(1)` 在**括号组 `(A)` 的关闭格**就 `IsBuildable → true`，`BuildByIndex` 拿
`calleeIndex = PreviousCode(tokenIndex-1)` ⇒ 取到 `new` 关键字，再往前一格 `newIndex` 取到的就是
`=` ⇒ 抛 `expression new 关键字`。`new /* c */ (A)(2)` 的注释是 trivia，`PreviousCode` 跳过后同样
落到 `new`，因此三条（以及整族）是同一个缺口。

对照 legacy `ExpressionBuilder.ParseNew`：它先 `ParsePrimary()`（`(` 走括号分支 ⇒
`ParenthesizedExpressionShape`），再吃被构造者的 `.` / `!` / `[` / 模板 / 类型实参后缀，**最后**才看
`(…)` 实参括号。所以 `new (E)(…)` 的正确树是
`NewExpressionShape[ ParenthesizedExpressionShape[E], …args ]`。

## 7. 结论

缺口不在「登记身份」（T13 已修），而在**建树格**：`new` 后面那只 `(` 是**被构造者**而不是实参括号，
而旧判据只看「已闭合的 `(` + 条目以 `new` 开头」。判别点只有一个：**前一个代码单元是不是 `new`
关键字本身**（`IsCalleeGroup`）。把这一格让出来之后：

- 括号组格不建树（后面还能接实参括号），实参括号格才建 `new (E)(…)`；
- 没有实参括号时（`new (E)` / `new (A);`）按无括号 `new C` 的同一条前瞻判据（`""` / `;`）在括号组格建树；
- 被构造者用 `ParenthesizedExpressionShape` + legacy `ExpressionBuilder.ParseExpression` 物化，
  与 `ParseNew → ParsePrimary` 的 legacy 树逐字段同源。

代价面：1716 条指纹 0 变化、30 target 不变、5 smoke 不变、旧矩阵无回归。
收益面：**fallback 46 → 43**（正是被修的三条），`new` 族 18 条矩阵 **12 FALLBACK → 0**，全部 judge ok。

遗留（未做，按「不改其它判据 / 不硬修」）：

1. `new (E)(…)` 后面接**三目**（`new (A)(1) ? 1 : 2`）仍 FALLBACK，首跳 `expression 条件表达式问号`，
   与 `new A(1) ? …` / `f(1) ? …` 同因，属条件表达式族，不在本轮；
2. `new (E)!…` / `new (E)[0]` / `new (E)<T>(…)` 由 legacy 在 EOF 收口（ok 但非增量建树），
   未在本轮改成增量建树（与 `new a.b.C()` 同一条既有口径）；
3. 43 条剩余 fallback 与 `new` 族无关。
