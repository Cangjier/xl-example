## 0. 结论

1. **首跳不是「三个关键字」的事，是「操作数位不认 `{`」**。R1236 只补了
   `IsStatementStart` 的「`{` 是值、不是块」那一半；值位**形状目录**里没有任何一条候选收
   **已闭合的 `{ … }` 括号**，于是 `}` 那一格上候选全灭：
   - `a in {…}` / `a + {…}` / `a && {…}` → `CatalogGuide: 没有候选形状可以构成（宿主 BinaryExpressionShape，下标 4）`
   - `a ? {…} : c` → 同一句，宿主 `ConditionalExpressionShape`，下标 3
   - `typeof {…}` → 不走目录：`PrefixUnaryPossibleShape.BuildByIndex` 只认 `Common` 操作数，抛
     `增量变量形状未支持：expression 前缀一元操作数`
   三条首跳全在 `a in { b: 1 }` / `a + { b: 1 }` / `a ? { b: 1 } : c` / `typeof { a: 1 }` 上**逐一复现**，
   不是 `{` 在值位被当成 block（角色解析那一层只是 `Fallback`，真正抛错的是**父形状的目录**）。
2. **修的是通用判据**：新增 `ObjectLiteralOperandPossibleShape`——「值位 `{` ⇒ `ObjectLiteralExpressionShape`」的
   **唯一一份**实现，接在三处操作数候选上（右操作数形态 / 三目成员 / 前缀一元）。判据只回答「形态」，
   「这是值位」由调用方的位置判据回答（前驱是运算符形状 / `?` `:` / 前缀运算符串），不新写位置词法。
3. **顺手发现一处既有拼写错**：`RightOperandFormPossibleShape.IsOperatorLike` 写的是
   `"InstanceofKeywordShape"`，而类名是 `InstanceOfKeywordShape`（大写 `O`）⇒ `a instanceof (b)` /
   `a instanceof "x"` / `a instanceof {…}` 这一族**形态**右操作数从来认不出前驱。
   改对之后 `instanceof` 那一格才通（矩阵里它是最后一个红的）。
4. **验收全绿**：`tshape-judge ts stmt-r1236` → `ok`（且 `FileFallbackCount=0`、wide structural=0）；
   矩阵 **11/11 ok**；默认档 `gates 4/0/7`、`wide-ast 0/2/73`、`real-dts PASS`、`tts 429`、`ts-all 426/0/3`；
   `--legacy` `gates 4/0/7`、`wide-ast 0/0/2`。**没有任何一条「原来通过现在失败」**
   （rest 的 2 条 DIFF / 3 条 ts-all 失败与基线逐字同身份）。
5. **副作用（好的方向）**：`tests/cases/token` 里**少了两条 fallback**：`stmt-r1236-value-word-brace.ts`
   与 `expr-ternary-object-branches.ts`（后者正是 `a ? {…} : c` 那一形，独立验证三目分支）。
   两条的增量树都与 TS 完全一致（wide-ast 不把它们记成 DIFF、`tshape-judge` 各为 `ok`）。

## 1. 首跳与根因（探针实测）

把 `EnableFileFallback=false`、在 `CatalogGuide.ComputePossibleShapesByIndex` 上包一层日志，逐条读
**抛错那一刻的宿主与 `Data`**：

| 用例 | 宿主 | `Data`（抛错格） | 抛错点 |
| --- | --- | --- | --- |
| `a in { b: 1 }` | `BinaryExpressionShape` | `[Identifier, Wrap, InKeywordShape, Wrap, {…}closed]` | `CatalogGuide`：`Candidates.size===0`（`EndPossible===null`） |
| `a + { b: 1 }` | `BinaryExpressionShape` | `[Identifier, Wrap, PlusTokenShape, Wrap, {…}closed]` | 同上 |
| `a && { b: 1 }` | `BinaryExpressionShape` | `[Identifier, Wrap, AmpersandAmpersandTokenShape, Wrap, {…}closed]` | 同上 |
| `a ? { b: 1 } : c` | `ConditionalExpressionShape` | `[Identifier, QuestionTokenShape, Wrap, {…}closed]` | 同上（目录只有 `ConditionalMemberPossibleShape`，它只认 `Common`） |
| `typeof { b: 1 }` | `VariableDeclarationShape` | `[v, =, typeof, Wrap, …, {…}closed]` | `PrefixUnaryPossibleShape.BuildByIndex`：「expression 前缀一元操作数」 |

读法（对应 R17 的两把尺子）：
- **`BinaryExpressionShape` 的右操作数目录** = `RightOperandPossibleShape.Catalog()`，五条候选：
  `RightOperandPossibleShape`（只认数字 / 标识符 `Common`）+ 四条形态（`(` / 字符串 / 模板 / 三个关键字）。
  **一条都不认 `Bracket`**，所以闭合那一格 `Reject` 到底 ⇒ `CatalogGuide` 按 C10 抛错 ⇒ `FileFallback`。
  这就是 R17 报的 `下标 4`（`Data` 的末位就那只 `{…}`）。
- **三目成员候选** `ConditionalMemberPossibleShape`：`before instanceof Common ? Accept : Reject`，
  同样没有括号位置。
- **前缀一元** 是**另一条路**：它在操作数那一格 `Accept`（`IsOperandPosition` 只看「前驱是前缀运算符串」），
  然后 `BuildByIndex` 只写了 `if (operandUnit instanceof Common) … else throw`。
  实测那一刻括号 **`Closed=true`**（`idx=6`，操作数是已闭合的 `{…}`），所以这里同样能整块建。
- 角色解析那一层（`BracketRoleResolver.Classify`）对这三格都返回 `Fallback("no-host-rule:…")`——
  它只是「不认领」，**不抛错**；抛错发生在闭括号回问父形状目录那一拍（`Bracket.Close` →
  `parent.ComputePossibleShapes`）。所以「是 `{` 在值位被当 block」这个方向不成立：它根本没被当成任何东西，
  就是**没有候选**。

## 2. 修法：一份实现，三处接线

新文件 `typescript/tokens/expressions/forms/shared/object-literal-operand.xl.md`（167 行 `.xl.md` → 125 行 `.ts`）：

| 成员 | 作用 |
| --- | --- |
| `static Claims(unit)` | 值位对象字面量的**形态判据**：`Bracket` 且 `Closed` 且 `StartBracketChar === "{"` |
| `ComputeByIndex` / `IsBuildable` | trivia `Uncertain` / 不建；形态不命中 `Reject` |
| `static BasePos(units, bracket, at)` | `ExpressionBuilder` 的 `Pos` 口径（前一个代码单元的终点） |
| `static BuildInto(host, codeIndex, context)` | **节点构造的唯一一份**：按宿主自己的 `Data` 用 `ExpressionBuilder` 装载 → `At` 指到括号 → `ParsePrimary()` → 必须**恰好**吃掉这一格 → 原位顶替（长度不变，调用方下标集合继续有效）→ 登记容器、`MountedUnit` 跟着换 |

`BuildInto` 与 `ContainerShapeCloseHook` 建对象字面量走的是**同一条 legacy 路**（`ParsePrimary` 整块吃掉括号），
区别只有「谁在什么时机调」：钩子要 `IsSafeHost`（只认 `VariableDeclarationShape`），本类不要求宿主类型。

三处接线（都是「位置判据在外、形态与建树在内」）：

1. `right-operand-possible-shape.xl.md`：目录加第五条形态 `Create("object", new ObjectLiteralOperandPossibleShape())`；
   `Claims` 加 `object` 分支；`IsBuildable` 对 `object` 只再确认形态。仍然由
   `ComputeByIndex` 的「前驱是运算符形状」保证**只在右操作数位**生效（初始化器起始格的前驱是 `=`，不被抢）。
2. `conditional-possible-shape.xl.md`：`ConditionalMemberPossibleShape.ComputeByIndex` 的中段（`?` 之后）与
   右段（`:` 之后）都接受 `Claims`；`BuildByIndex` 对应两处改走 `BuildInto`（右段仍照旧封口 + 卸载宿主）。
3. `prefix-unary-possible-shape.xl.md`：`BuildByIndex` 的 `else throw` 前加一支「操作数是值位 `{…}`」→
   `BuildInto`，`operandEnd` 取建出形状的终点（后面的「自右向左逐层包」一字未改；`BuildInto` 原位顶替、
   长度不变，`removed` / `kept` 的下标集合继续有效）。

**为什么不是「只修 `in` / `instanceof` / `typeof`」**：`a + {…}` / `a && {…}` / `a ? {…} : c` 与它们同一条首跳
（对照表见 §1），修三个关键字等于把同一格修三遍还漏三格。**为什么不是退回 fallback**：修之前这几条正是靠
fallback 才「看起来对」，而 R17 §1.2 已证明 fallback 那一遍在整文件上会丢尾部 `TryStatement`。

## 4. 顺带修掉的既有拼写错（`instanceof`）

`RightOperandFormPossibleShape.IsOperatorLike` 原来：

```ts
return name === "InKeywordShape" || name === "InstanceofKeywordShape";   // 类名实际是 InstanceOfKeywordShape
```

实测：`a instanceof { b: 1 }` 抛错格的 `Data[2]` 是 `InstanceOfKeywordShape`，`IsOperatorLike` 返回 `false`，
新增的 `object` 形态在 `ComputeByIndex` 里就被 `Reject`——**矩阵最后一条红的就是它**。
`in` 的类名是对的（`InKeywordShape`），所以同为关键字运算符的两格命运不同。

只认结构名、不读文本；改法是把两种拼写都放行（`InstanceOfKeywordShape` 为真名，`InstanceofKeywordShape`
保留以兼容旧产物），并把这条写进该方法的文档。副作用是同一族**形态**右操作数一并转绿：
`a instanceof (b)` / `a instanceof "x"` / `` a instanceof `t` ``（此前同样在右操作数格上目录全灭）。
